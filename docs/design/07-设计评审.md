## 3. 未落地 / 部分落地项的裁决

每一项给出**引入或放弃**的明确结论与理由。

### 3.1 业界成熟方案的「意图分析 + 目录递归 + rerank」—— **放弃，但需写明补偿**

**裁决：放弃。**

- **意图分析**（LLM 生成 0–5 个 typed query）需要**每次召回多一次 LLM 调用**——器灵的 `prefetch` 是每轮对话都跑的热路径，成本与延迟都不可接受
- **目录递归检索**依赖"URI 寻址 + 目录树"的文件系统范式，而器灵采用结构化真相源（INV-1），没有"目录"这个概念
- **rerank** 需要额外模型或 LLM 打分，同样命中热路径

**补偿方案（已存在，但未显式对齐）**：多因子融合召回（AL2 §5 M5）用"语义 + 活性 + 扩散 + 时间 + 核心一致性"五路打分替代 rerank；用"层 + `scope` 过滤"替代目录递归。

> **边界澄清（2026-09-15）**：放弃的是"**以文件系统目录树作为存储 / 检索主结构**"。**知识型记忆**（外部资料积累）的"**目录卡**"不是目录树，而是每条记忆上的一条极短索引字段（复用 `abstract`，约 24 token），仍在结构化真相源内，**不违反 INV-1**——见 [DES-RES-004 §3.2 / §4](./11-知识型记忆研究与机制增补.md)。

> **需要动作**：在 LLD-AL2 §5 M5 补一段"与业界成熟检索范式的对照说明"，把"放弃什么 / 用什么补偿"写清。否则未来读者会以为这是遗漏。

### 3.2 Mem0 的「实体匹配信号」—— **建议引入（M1）**

**裁决：建议引入。**

- 器灵已有 `entities` 表和 `relations(rel_type='mentions')`，**数据结构具备，只差把它接进召回打分**
- 实体匹配对"问某个项目/人名"这类查询特别有效，而器灵的目标场景（个人助手记忆）恰好高频出现实体
- 成本为零：实体抽取已包含在提取环节，召回时只是多一路 SQL 匹配

**建议做法**：在 `RecallWeights` 增加 `entity` 权重项（默认 0.10，从其他项等比压缩），融合公式变为六因子。

> **需你确认**——这会改动 [LLD-AL2 §2.2](./layers/AL2-核心层详细设计.md) 的 `RecallWeights` 与 M5 公式。

### 3.3 Graphiti / Mem0 的「双时态语义」—— **MVP 只留字段，M3 启用**

**裁决：分阶段。**

- 器灵的 `valid_from` / `valid_to` 字段已建，但**没有任何代码路径写 `valid_to`**——因为写它的是 `INVALIDATE` 决策，而 `INVALIDATE` 延后到了 M3
- 结果：MVP 阶段这两个字段恒为 `valid_from=<写入时间> / valid_to=NULL`，**时序模型形同虚设**

**理由与风险**：这不是错误，但**必须在非目标清单里说清**，否则会出现"字段建了却不生效"的隐性契约违背。真正要做的是让 `valid_to` 有写入路径（M3 的 INVALIDATE），并让召回支持"as-of 查询"（回答"当时什么是真的"）。

> **需你确认**：MVP 是否接受"字段预留、语义 M3 启用"？若接受，需在 [DES-000 §1.2 非目标](./00-方案设计.md) 与 LLD-AL3 补注。

### 3.4 LangMem 的「自更新指令层」—— **放弃**

**裁决：放弃。**

- 该能力（让记忆系统生成/更新自己的行为指令）与 **Hermes 的 skill 体系**功能重叠，器灵再做一遍是重复建设
- 器灵的程序性记忆层已经承担了"可复用轨迹"的职责，二者边界会打架

**替代**：程序性记忆（**M2 语义 → 程序** 固化）承担"经验模式"，skills 交由 Hermes 原生体系管理（边界与机制详见 [DES-RES-005](./12-程序性记忆与技能机制增补.md)）。

### 3.5 A-MEM 的「记忆进化」—— **建议部分引入（M4）**

**裁决：建议部分引入，与扩散激活同批。**

A-MEM 的核心是：**新记忆入库时，触发对已有相邻记忆的上下文/关键词/标签更新**（Zettelkasten 式自组织）。

- 器灵目前只做了"建边"（Hebbian 共激活），**没有做"被激活记忆的自我更新"**
- 这是有真实价值的一环：一条新记忆可能让旧记忆的关联更丰富，但器灵当前只增加边权，不更新旧记忆内容
- 成本可控：与 M4 的扩散激活共用 `relations` 基础设施

**风险**：如果做过头会变成"记忆自我修改"，破坏 INV-1 的可审计性。**建议限定为"只更新 `abstract` 与关联边，不改 `content`"**。

> **需你确认**——涉及是否在 M4 增加一个机制（M6）。

### 3.6 Mem0 的「六态更新」—— **MVP 三态，M3 补齐（需记录为决策）**

**裁决：分阶段，但必须显式记录。**

- RES-001 §5 的动作项写的是"MVP 直接落地六态"，而 LLD-AL2 实际只做三态——**这是一处未记录的偏差**（P1-1）
- 理由站得住：`INVALIDATE` / `FORGET` 依赖时态与衰减模型（M3），`MERGE` 依赖相似度阈值调优
- 但"没记录"就是问题：未来的读者会认为设计漏了

### 3.7 Graphiti 的「nodes / edges / facts 三表」→ 归并为「memories + entities + relations」

**裁决：归并，但说明在重构中丢失（P1-2，已修）。**

RES-001 §4.3 提的是 `nodes` / `edges` / `facts` 三表；LLD-AL3 落的是 `entities` / `relations` + `memories`。

- **归并理由**：`facts` 与 `memories` 是同一个东西（都是"带主语谓语宾语的事实陈述"），分成两表会导致**两套事实真相源**——直接违反 INV-1
- **正确表述**：`memories` 是所有层的统一真相源；`entities` 是实体节点（≈ nodes）；`relations` 是关联边（≈ edges）；**事实只存 `memories` 一份**

> 这个说明在 v1.0 的 00 文档中存在，但在"概要设计拆分"时**丢失**了。**已在本轮补回 LLD-AL3**。

### P0-3 `runtime/threading_.py` 违反了自己的 R4

```python
# 修订前（runtime/threading_.py）
def resolve_host_thread_factory() -> ThreadFactory:
    try:
        from agent.memory_provider import spawn_context_thread   # ← 宿主耦合在 AL5
```

**讽刺之处**：这个模块的 docstring 里**正写着**"runtime 不 import 宿主"。R4 修好后它立刻变红——**这说明 P0-2 的修复真的在管事了**（一个洞被补上，立刻抓到一条真实的越界）。

## 11.6 规则集变更：R1–R8 → R1–R10

| 规则 | 变更 | 理由 |
|---|---|---|
| **R1** | 明确 `core/*`、`extract/*` **只能**依赖协议 + 共享内核 | 原表述没写 extract，检查器也只查 core |
| **R3** | 增补"**不得引入 `openai` SDK**" | 与 AL4 §1.2 的声明对齐；原规则漏了这一条 |
| **R4** | 从"核心层禁止依赖 Hermes"改为"**只有 `provider.py` 可依赖宿主，其余一律禁止**" | 原表述是"唯一豁免点 + 一条禁止"，**豁免点没写进规则**，检查器也就没法放行它（P0-2 的死代码正源于此）。改写后：豁免点是规则的**目的**，不再需要第二条规则来兜 |
| **R8** | 增补"**也只有 `runtime/` 能用并发 / 异步原语**" | 原规则只禁"创建线程"，`asyncio` / `concurrent` 可以随手 import |
| **R9** | **新增**：层内实现模块不可跨层（`store.sqlite_backend` / `model.resolver` / `model.openai_compat`） | 白名单只能约束"往哪去"，管不住"**从哪来**"。`sqlite_backend` 一旦被 AL1 导入，连 sqlite-vec 一起拖进最外层——实现细节变成事实上的公开 API（P1-1 的由来） |
| **R10** | **新增**：AL5 不得依赖业务层实现，**唯一例外是组合根 `runtime/lifecycle.py`** | 支撑层没有边界就会退化成第二套业务实现入口（P0-2 第四个洞） |

**两处刻意的设计选择**：

1. **检查器改为自研**（`compliance/arch_rules.py`，零依赖）。`import-linter` / `pytest-archon` 只能表达"包 A 不许 import 包 B"，而本轮四个洞**全部在包级之外**：宿主要按**点分路径**匹配、实现模块要按**模块名**点名、例外要精确到**单个文件**、还要守住"新增包必须登记层表"。自研的额外收益是**规则即代码**——不存在"文档改了、门禁没改"的漂移。
2. **例外必须写进规则，不能靠"整层放行"**。R9 与 R10 都把例外收敛到 `runtime/lifecycle.py` **一个文件**，并各自配了一条"例外只给这一个文件"的测试（同名的 import 放在 AL5 别处必须红灯）。**"整层放行"是边界失效最常见的形式**——它看起来像宽容，实际是把约束取消了。

## 12.3 P0（✅ 已修）

### P0-1 `aspirit status --json` 这条验收命令根本跑不通

`--json` 只定义在**顶层解析器**上，于是只有 `aspirit --json status` 能用；而 LLD §8.4 与 T-AL1-08 的验收原文写的都是 `aspirit status --json` —— 实测直接：

```
unrecognized arguments: --json   →  exit 2
```

**为什么是 P0**：这不是"文档笔误"，而是**验收条件与实现互相矛盾**，且**测试把验收原文改写成能过的顺序**（`main(["--json", "status"])`）后一切正常。也就是说，**一条写在验收清单里的命令从来没被真正执行过**。这类"测试替验收改题"的现象比命令本身跑不通严重得多。

**修法**：让两种位置都成立（在 `build_parser()` 收尾处给每个子命令统一补 `--json`），**而不是把文档改成实现的样子**——文档全篇与集成脚本都在用前一种写法，改文档等于把偏差扩散给所有调用方。`default=argparse.SUPPRESS` 不能省：`_SubParsersAction` 会把子解析器的默认值**回写覆盖**顶层已解析的值，写成 `False` 会让 `aspirit --json status` 反而退回人类可读分支（这个坑本次实测踩到了）。

**新增用例**：`test_cli_accepts_json_after_subcommand_too`（两种位置都断言）、`test_every_subcommand_declares_json_flag`（防止将来新增子命令漏掉）。

### P0-2 `aspirit status` 在 Windows 控制台上直接崩掉

`status` / `doctor` 的输出里带 `✅` / `⚠️`，Windows 默认控制台是 GBK，装不下这些码位：


**为什么是 P0**：`status` / `doctor` 是**排障主入口**，而它在报障者的机器上**自己先倒在编码上**，用户看不到任何体检结果。而且本项目的开发环境就是 Windows（本轮实测复现）。

**两方论证**（这才是裁决点）：

**甲：保留 v1（不声明），改文档**

- 宿主 ABC 写的**声明前提器灵满足不了**：`durably checkpoint **every successful** on_pre_compress()`。器灵做的是 `maintenance.schedule({...})` 投递给后台 writer，由它执行巩固（**要调 LLM 抽取**）。**投递 ≠ 完成**，成功与否还取决于 LLM 与存储——"every successful" 保证不了。
- 于是**声明 v2 就是虚假声明**。代价不是"少了个能力"，而是宿主会**按我们的承诺行事**，然后在我们保证不了的那条路径上失败。
- v2 的同步确认语义与 **E6「绝不阻断宿主」**直接冲突：压缩是宿主的动作，器灵不该让它因自己失败。

**乙：改实现做 v2**

- 宿主 strict 模式下，不声明 v2 的 provider **不参与 fail-closed 保证**——宿主那侧对这段记忆交接没有任何保证，器灵也没有机会阻止"压缩成功但记忆没保住"。
- **技术上可行**：strict 模式下**同步**把原始消息写一条快照到本地 SQLite（ms 级，正对 ABC 说的 `normalized evidence handoff`），异步巩固照旧。这样 "durable" 只承诺"**证据已落盘**"，不承诺"结构化巩固完成"——恰好落在 ABC 措辞的灰区里。
- 代价：主线程多一次同步落盘（**须改任务书验收项 3**）；且 strict 模式下**任何**失败都必须能被感知并抛出——包括后端不可用、磁盘满、锁冲突，而这些正是现在 `except Exception: return ""` 吞掉的。

### P1-4 `prefetch` 超时路径把副作用留在"被放弃的线程"里

[runtime/timeout.py](../src/artifact_spirit/runtime/timeout.py) 的 docstring 声称："被遗弃的线程会自然结束——它的结果没人要，但**也不会影响正确性**"。

**这条声明与 AL1 的实现冲突**：传给 `run_with_timeout` 的闭包**会写 `self._last_recall` / `self._last_injected`**。超时后该线程仍可能跑完，于是：

1. **迟到的召回 id 被挂到下一轮**：下一轮 `sync_turn` 会把 `_last_recall` 当作 `TurnEvent.recalled` 上报——**给一条本轮根本没被召回的记忆记一次访问/共激活**（活性污染，且是静默的）
2. **`recall_status()` 报陈旧条数**：超时路径不重置 `_last_injected`，于是指示器显示**上一轮**的条数——而宿主契约明令"**Must reflect only the LAST prefetch, never a stale prior count**"

**建议**：(a) 闭包内只在"未被放弃"时才写状态（传入一个 `cancelled` 判定）；(b) 或超时分支显式重置 `_last_recall` / `_last_injected`；(c) `timeout.py` 的 docstring 必须修正——**它现在给了一个错误的保证**。另需补两条测试（超时后 `recall_status()`、超时后下一轮 `recalled` 归属）。

**处置（2026-09-16）**：✅ 已按 (a) + (b) + (c) 三管齐下。

- `provider.prefetch` 传给护栏的闭包改成**只算不写**（`run()` 只返回 `(文本, ids)`），状态一律由**主线程在未超时分支**里写——从根上切断了"被遗弃线程改共享状态"的路径，而不是靠超时分支去补救。
- 超时分支与 `except` 分支**双双显式清空** `_last_recall` / `_last_injected`：宿主契约要求 `recall_status()` "只反映最近一次 prefetch"，而"这一次什么都没注入"就必须是 0 条，不能显示上一轮的陈旧条数。
- `runtime/timeout.py` 的 docstring 重写：明确"**结果没人要 ≠ 没有影响**"，把"`action` 必须无副作用"写成对**调用方**的硬约束（此前它给的是一个错误的保证）。

## 12.6 关于「验收要求本身是否合理」的判断

这是本轮的**主要问题**。逐条读完 13 个任务后，把验收要求分成三类：

### ✅ 好的一类：行为级、可机械判定、能真的失败
`p99 < 5ms 且无 I/O`、`socket 打桩断言零网络`、`白名单外的键被忽略`、`无确认不写库`、`schema 与 handler 一一对应`、`密钥只走 env`。

这些要求的共同点是**指定了"怎么证明"而不只是"是什么"**。相比之下，同一份清单里的 `--help 正常` 就只能靠人工——不是错，但应当注明"本项目无自动化证据"。

### ⚠️ 有问题的一类：**可被最弱形式满足**
- `test_system_prompt_block_has_budget`：参数给了 100，断言写 1200（**即使参数被忽略也过**）
- `test_invariant_inv5_no_network_in_is_available`：`assert resp.ok in (True, False)`（**恒真**）

**这类断言的危害不是"漏测"，而是"给了覆盖的错觉"**——与第三部分那条死规则（R4）是同一个病：**门禁看起来在工作**。建议把"弱断言"当成一类缺陷显式排查：**任何"即使把被测逻辑删掉也能通过"的断言都必须重写**。

### ❌ 有问题的一类：**验收原文与测试不一致**
`aspirit status --json`（验收原文）vs `main(["--json", "status"])`（测试实际）。修好实现后两种都成立，但**根本问题没解决**：**验收清单里的命令没有被真正执行过**。

**一条可复用的规则**（建议写进 [DES-CHARTER](./08-设计纲领.md) 的工程原则）：

> **验收清单里的每一条命令、每一个数值，都必须是逐字被执行过的。**
> 可以被改写、可以被简化的，都不是验收。

## 12.8 验收与用例的同步规则（已升为 E7）

> 本节回答一个比"哪条验收没测"更根本的问题：**验收要求为什么会与用例脱节，冲突时该改哪一边。**

### 为什么要在设计评审里管这件事

复核 AL1 时实测到三类现象，它们**同源**：

| 现象 | 实例 | 危害 |
|---|---|---|
| **验收原文被用例改写成"能过的形式"** | 验收写 `aspirit status --json`，用例写 `main(["--json", "status"])` | 验收清单里的命令**从未被执行过**，偏差存活了整个里程碑 |
| **断言弱到无法失败** | `assert resp.ok in (True, False)`；传 `token_budget=100` 却断言 `len(block) < 1200` | **假覆盖**——门禁绿着，守卫已经空了 |
| **条款过时，用例还钉着它** | 任务书曾要求"采用 v2 checkpoint API"，用例 `test_pre_compress_does_not_claim_checkpoint_api` 钉住相反行为 | 编码端两头堵——**满足用例就不满足条文**（P1-3，2026-09-16 已裁决为"改文档"） |

三者的共同点：**门禁看起来在工作，实际守卫的是一份已经过期的设计。**

### 根因：验收要求散落在两处，同步全靠人

AL1 的验收要求同时存在于**两个地方**，且两处**并不完全重合**：

- **LLD §8 验收清单**（如 §8.3「所有产出路径位于 `hermes_home` 之下（INV-9 断言）」）
- **编码任务书的 `T-AL1-xx` 验收项**（13 个任务）

改设计时改一处、另一处不知道；**用例挂在哪一处也没有记载**。既然没有"验收项 ⇄ 用例"的对照，"用例过时"就**既不会被发现，也不会被追责**——它只能靠人偶然读到，而读到的时候往往已经写了一批迁就旧用例的代码。

### 处置：升为工程约束 E7（详见 [DES-CHARTER Part B](./08-设计纲领.md)）

**裁判顺序**（上游裁判下游）——冲突时先定位"哪一层先偏离"，再决定改哪一边：

```
功能设计意图 > LLD 契约条款 > 编码任务书的验收项 > 用例 > 实现
```

**三类处置**：用例与条款不符 → **改用例**；条款文字与设计意图不符 → **改文档**（并同步该条款的用例）；实现未兑现条款 → **改实现**。

**两条禁止**：禁止为让门禁变绿而**降低断言强度**；禁止**改实现去迎合一个与设计不符的用例**——那等于让过时的用例决定产品走向。

**AL1 冲突逐条定性**（按 E7 判定"谁错、改哪边"）：

| 冲突 | 谁偏离 | 处置 | 状态 |

## 12.9 追溯矩阵自身的失效（2026-09-16 实测——E7 的第一次"反噬"）

> **一句话**：把"缺口必须留痕"做成可执行约束之后，**第一个被抓出来的缺口是矩阵自己**。

### 现象一：8 处引用指向**不存在**的用例名

`test_referenced_tests_exist` 报红，逐条核对后分两类：

| 类型 | 实例 | 成因 |
|---|---|---|
| 弱用例被删后没同步 | `test_invariant_inv5_no_network_in_is_available`、`test_sync_turn_is_fast_and_non_blocking`、`test_sync_turn_does_no_io` | P1-6 删弱版时只动了用例，矩阵还钉着旧名字 |
| 把"计划要写的用例名"当成了**已存在**的名字 | `test_save_config_filters_secrets`、`test_system_prompt_block_has_budget`、`test_value_v3_export_is_portable` | 建表时按**意图**填名字，而不是按**实际函数名**填 |

后一类更值得警惕：**它让"计划"看起来像"证据"**——直到有人真的去跑那条断言。

### 现象二（更隐蔽）：**已覆盖**的条目仍记作 `gap`

P1-5 的 9 条补测**早已落地**，矩阵却仍把 INV-9、entry point、CLI 命令集、`--help`、`on_memory_write` 镜像等记成 `gap`。

这类偏差**不会报红**：校验器只检查"非 `covered` 是否带裁决编号"，**无从判断一个 `gap` 是否已经过期**。

> **两个方向相反的偏差，同一个性质：矩阵在说谎。**
> 前者的红灯靠"用例名必须真实存在"这条校验才发现；后者**没有任何自动信号**，只能靠**逐条核对真身**（本次逐条比对了 AL1 的 51 + 9 条用例）。
> 这条经验应写进逐层复核的取样口径：**矩阵条目要与用例清单「双向」比对，而不是单向校验。**

### 处置

1. AL1 矩阵按"逐条核对真身"**重建**：每条 `covered` 都指向真实存在且断言相称的用例；各批处置结论分别落在 `note` 里（P0-1 / P1-2 / P1-3 / P1-5 / P1-6 / P2-6 / P2-7）。
2. `test_value_v3_export_is_portable` 是唯一"矩阵先声明、用例后补齐"的条目——按 E7，`gap` 的处置是**补用例**，所以补的是用例（真做"导出 → 纯文本可读 → 导入**全新库**内容不丢"的端到端往返），**不是把矩阵改弱**。
3. `T-AL1-13` 由 1 条拆为 5 条（V1 / V2 / V3 / INV-4 / INV-5），与任务书的五条验收项一一对应——原先把三条核心价值挤在一行，正是"**一条断言替三条条款背书**"的温床。
4. 顺带实测发现的实现缺陷：`on_memory_write("   ")` 会落一条空记忆（`"   "` 是 truthy，`not content` 挡不住），已改判 `content.strip()`。

> **结论**：E7 这一轮实战的价值不在于"抓出了几个缺口"，而在于**证明了"缺口可执行化"这条路是自洽的**——矩阵一旦说谎，就会被自己的校验器抓住。

## 13.3 P0（⏳ 待裁决 / 待修）

### P0-4 召回热路径的实体因子是"全表扫描 + 静默截断"（**与设计声明相反**）

LLD 对这条因子的成本承诺是白纸黑字的（`:450`）：

> **成本为零**：实体抽取在提取环节已完成，召回时**只是多一路 SQL 匹配**。

`core/recall.py::Recaller._entity_index` 的实现：

```python
for entity in entities:                                   # 每个命中实体
    ...
    for record in self.backend.query(status=None, limit=500):   # ← 每次一条全表查询
        if entity.casefold() in (record.content or "").casefold():   # ← Python 侧子串扫描
```

**两个问题叠加**：
1. **成本**：一次 `recall()` 的实体路成本 = `实体数 × 500 行读取 + 字符串 casefold 匹配`。而 `recall` 是 **AL1 `prefetch` 热路径**（p99 目标 5ms 级、prefetch 护栏 300ms）——这是**唯一**把全表遍历放进热路径的因子。
2. **正确性**：`limit=500` 无排序保证，"取哪 500 条"未定义 → **库变大后实体因子的兜底匹配会静默失真**（排序上浮承诺 `§8` 第 686 行"提及该实体的记忆排序上浮"在高基数下不成立）。

**裁决建议（甲 / 乙）**：
- **甲（推荐）**：删掉全表兜底，实体路只走已建的关系边——`backend.entity_find(text)` → `neighbors(id, rel_type="mentions")` → 计候选出现次数。关系边是**提取期**写入的（正是 LLD 说的"成本为零"），召回期只做索引查询。
- **乙**：保留兜底但**显式付代价**——把 `limit=500` 提为配置项、在 LLD 写明"兜底路 O(500) 上界"、并补一条"注入 1 万条记忆时该路查询行数 ≤ 上界"的用例。

> 无论选哪个，`§8` 的实体验收项都必须补一条**成本断言**——现在它只断言"排序上浮"，断言不出"成本为零"。

### P0-5 `HealthReport.promoted_candidates` 传的是"活跃总数"（字段撒谎）

`core/facade.py::health()` 末尾：`promoted_candidates=active`。而该字段在 §2.1 契约里的语义是**可提升候选数**（巩固判据命中但尚未提升的条数）。后果：`aspirit reflect` / `spirit_health` 恒显示"可提升候选 = 全部活跃记忆"——**一个永远在撒谎的健康指标比没有指标更坏**。

### P0-6 MERGE 决策：审计写 `merge`、动作是新增（审计账本与事实不符）

`core/facade.py::_extract_and_dedup` 的决策→审计映射含 `"MERGE": "merge"`，但分支实现是 `else: ... put`——即 **MERGE 落到 ADD 的路径上**。于是审计里出现一条 `op="merge"` 而实际新增了一行记录：**INV-7/8 的可审计性在去重这条链上是假的**（后续想审计"合并过什么"会读到空）。

### P0-7 `superseded_by` 全库无生产者 → D-23 的"错误/冲突记忆"删除路径缺席

`T-AL2-15` 要求 1 写**三类触发**（错误记忆 / 冲突记忆 / 不可达记忆），`OptimizationReport` 的 docstring 也照抄了"三类触发（D-23）"。实际：

- 实现只有两类：**不可达 → `forget`**、**无入边 + 低重要度 → `dormant` 降级**；
- `superseded_by` 字段**没有任何写入方**（全库只有 schema、SELECT 列、和 `Optimizer` 读它的意图）——连"错误记忆"的判据都无从命中。

## 13.6 关于「验收要求本身是否合理」的判断（AL2）

与 12.6 同法，逐条读完 15 个任务的验收后，**三类问题的分布与 AL1 不同**：

### ❌ 最要紧的一类：**验收口径不可机械判定**（AL2 独有）

`T-AL2-01` 验收 #1 = "**`CoreFacade` 方法签名与 LLD §2.1 一致**"。这条要求：

- **无法自动判定**（要人同时读两处，且要判断"缺方法算不算不一致"）；
- **已经不一致了整整一个里程碑而无人发现**（LLD 缺 3 个入口、`on_session_end` 返回类型不符）。

**根因**：契约的**权威副本被写了两遍**（LLD §2.1 与 `facade.py`），而"两遍一致"这件事没有可执行载体。这正是 12.8 里"追溯矩阵"要防的形态——只是它防的是"验收项 → 用例"，这里缺的是"**契约 → 实现**"。

**建议（可执行化）**：把这条验收改造成**白名单式断言**——用例里列一份 `CoreFacade` 公开方法集合的期望清单，用 `inspect` 比对。**契约少写一个入口也会红**，而不是靠人读。

### ⚠️ 第二类：**要求与验收范围不一致**（P1-3 同型）

`T-AL2-15` 要求 1 写**三类触发**，验收 4 条**只验了"不可达"与"时间/频率不参与判定"**——"错误/冲突记忆"既无实现也无验收（P0-7）。**要求比验收宽，宽的这部分就是没人守的边境。**

### ⚠️ 第三类：**验收项与不变量冲突**

`T-AL2-08` 要求 7「输出为人类可读文本（V2）」与 INV-1 冲突（P1-17）。这与 AL1 的 P1-3 是同一类：**条款是旧设计的化石**。

### ✅ 好的一类（AL2 的主体）

`§8.x` 里那些"注入即翻红"的断言做得很好，例如：`importance 与 access_count 解耦`（D-20）、`热路径不生成 L1`（N-P0-2）、`降级只产生 active→dormant，不存在 archive 目标状态`、`decay() 不产生 hard_delete 调用`（红线）、`巩固幂等`。**AL2 的用例密度与断言强度明显高于 AL1**——这也是本轮 P0 没出现崩溃类问题的原因。

### 追加一条工程结论（建议并入 E7 的判据）

> **"与 X 一致"不是验收。** 任何形如"签名/字段/枚举/清单与某文档一致"的验收项，**必须给出可比对的两侧与判定方式**；
> 否则它不是验收，而是一句愿望——**AL2 用 15 个任务证明它会漂移。**

## 14.3 P0（2 条）

LLD §M11 二（环节表第一行）写：

> 删除前：`audit(op='forget').before` 写入 `MemoryRecord` 的**完整快照**（含 `content`…）；与 `hard_delete` **同事务**

而实现是**另一套设计**：快照写进独立的 `delete_snapshots` 表，`audit` 只记账本，`schema.sql` 里还给了理由（"audit 是 append-only，合规删除要求内容真的不存在"）。

**为什么这是 P0 而不是"实现细节"**：

- §M11 二 的同一节又写 `purge_snapshot=True` 是「**合规**删除」。若按文档实现（内容进 `audit.before`），而 `audit` 被触发器**禁止删除**，则**合规删除根本做不到**——文档描述的方案自相矛盾；
- 反过来说，实现的分表方案是**唯一能同时满足 INV-8（append-only）与合规删除**的形态。**这属于"照文档做会做出坏东西"**，不是风格差异。

**处置**：LLD §M11 二 已按实现重写（并附"为什么不放 `audit.before`"）；§M4 补 `delete_snapshots` DDL 与理由；§8 补一条"清点快照"断言。

### P0-9 FTS 方案：文档写外部内容表、注意事项写 `'delete'`，实现是普通表——**两边照着做都会坏**

- LLD §5 M4 的 DDL 写 `content='memories', content_rowid='rowid'`（外部内容表）；
- §6 **C5** 写"FTS5 删除必须走 `'delete'` 语法；**直接 `DELETE FROM mem_fts` 会破坏索引一致性**"；
- 实现是**普通 FTS5 表**（`tokenize='unicode61 remove_diacritics 2'`），删除**恰恰**用 `DELETE FROM mem_fts`，并额外注册 `spirit_norm()` 做中文逐字归一化（触发器里写入的是归一化后的文本）。

**危害是双向的**：

- 信文档 → 建外部内容表 → 中文检索命中率崩（未归一化）；
- 信 C5 → 在普通表上硬套 `'delete'` 语法 → 索引与表不一致，且**这种坏法不会报错**（FTS5 对不匹配的内容表内容只是静默错乱）。

**处置**：§M4 已按实现重写（含"为什么是普通表"），触发器 DDL 改为 `DELETE`，**C5 整条改写**。

## 15.3 P0（2 条）

### P0-10 `_materialize_host_node` 把 host 段写进**错误的链** → embedding 被判成不可用（**已修**）

`resolver._materialize_host_node()` 被 `_host_llm()` 与 `_host_embedding()` **共用**，而它失败时固定写 `self._embedding_chain`：

```python
        key_env = str(node.get("api_key_env") or "")
        if key_env and not self._env.get(key_env):
            self._embedding_chain.append(          # ← LLM 路径进来时，也写 embedding 链
                {"source": "host", "usable": False, "reason": f"环境变量 {key_env} 未设置"}
            )
            return None
```

**为什么它是 P0 而不是"显示错"**：`_probe_embedding()` 的解析判据是
`if self._embedding_route is None and not self._embedding_chain`——**"链非空"被当作"该链路已解析完成"**。
污染一条无关条目，就让 embedding **整段跳过解析**：合法配置从不被读取，`embedding_available()` 返回 `False`，
上层据此**静默降级 BM25**（INV-6 的降级路径被误触发），而用户看到的是"embedding 没配"。

**逐字复现**（`[models.embedding]` 完全合法，只是宿主 LLM 节点的 `api_key_env` 指向未设置的变量）：

```
llm_available= False
embedding_available= False        # ← 错！embedding 配置是齐备的
embed_chain= [{'source': 'host', 'usable': False, 'reason': '环境变量 MISSING_XYZ 未设置'}]   # ← 这是 LLM 解析产生的
```

修复后（同一命令）：

```
embedding_available= True
embed_chain= [{'source': 'spirit', 'usable': True, ...}]
llm_chain= [spirit↓, host(环境变量 MISSING_XYZ 未设置), host(宿主配置中未找到可用模型服务), task(none)]
```

**可达路径**：`observability/status.py` 在同一函数里**先** `resolve_chain('extract')`（第 73 行，触发 LLM 解析）
**再** `embedding_chain()` 与 `_degradations()` 里的 `embedding_available()`（第 96 行）；`doctor()` 的
`embedding_available()`（第 216 行）若跑在 `report()` 之后同样中招。
即 **`aspirit status` / `aspirit doctor` 会把配置完全正常的 embedding 报成不可用**，并显示一条根本不属于 embedding 的链段。
正常启动路径（`lifecycle` 先调 `resolver.embedding()`）侥幸躲过功能影响，但链展示仍是错的——**这种"运气型正确"本身就是风险**。

**处置**（本轮已落地）：

1. `_materialize_host_node(node, chain)` 显式接收**调用方所属**的链，两个调用点分别传 `self._llm_chain` / `self._embedding_chain`；
2. AL4 LLD **§6 新增 C11**（"链信息只由对应的解析器写"）——把教训变成可引用的规则，否则下一个人还会写错；
3. `tests/test_model.py` 新增 `test_llm_chain_failure_does_not_disable_embedding`（**顺序敏感的回归用例**：先 `llm_available()` 再 `embedding_available()`，并断言 embedding 链里不含 `host` 段）与 `test_llm_host_segment_reports_which_key_env_is_missing`；
4. 验证：`pytest tests/test_model.py tests/test_al5_runtime.py` → **97 passed**。

> **附带发现**：修好之后 LLM 链里同一段 host 失败会出现**两条**（"环境变量 X 未设置" + "宿主配置中未找到可用模型服务"）。
> embedding 路径本来就是这个形态（同样的重复），属既有约定，故本轮**不为它重构**，只登记为 P2-22。

### P0-11 F7「AL4 启动即抛错」**要求 AL4 做架构上禁止它做的事**

LLD §7 故障表原文：

> | **F7** 维度不匹配 | `dim` 与配置/库不一致 | **启动即抛错** | AL1 → 拒绝启动并提示 `reindex` |

但"库"对 AL4 是不可见的：R3 明令 AL4 不得依赖 `store/*`，而维度活在 `meta.embedding_dim` 里。
**照文档实现只有两条路**：违反 R3（架构检查报红），或写不出来（验收项不可满足）。
这属于"**照文档做会做出坏东西 / 做不出来**"，与 AL1 的 P0-1（验收命令根本跑不通）同型。

三处说法本来就互相不一致：LLD §7 F7 说"AL4 抛错"、§6 C4 说"启动时与 `meta.embedding_dim` 比对"（在哪启动？），
任务书 T-AL4-07 说"由 AL5 装配期调用"。

**实际（正确的）职责划分**：

| 环节 | 归属 | 证据 |
|---|---|---|
| 从配置/已知模型表得到 `dim`，非法即抛 | **AL4** | `resolver._embedding_dim()` |
| 读 `meta.embedding_dim` 并与配置比对 | **AL3** | `SQLiteBackend.assert_embedding_model` / `DimensionMismatchError` |
| 装配期拒绝启动 + 提示 `reindex` | **AL5** | `runtime/lifecycle.py` 传 `cfg.embedding_dim`；`observability/status.py` 的"向量维度一致性"检查 |

**处置**（本轮已落地）：§7 F7 行改写为"AL4 不做这个比对"；§6 C4 改为"AL4 只保证 dim 来自配置或已知模型表且为正整数"；
§5 M7 补 `dim` 判定三步（显式配置 → `KNOWN_EMBEDDING_DIMS` → **抛错，绝不给默认维度**）。

## 15.6 关于「验收要求本身是否合理」的判断（AL4）

### ❌ 要求 AL4 做架构上禁止它做的事（P0-11）

§7 F7「AL4 启动即抛错」与 T-AL4-07 验收「与库中记录不一致时可抛出」——
两条都要求 AL4 触碰 `meta.embedding_dim`，而 R3 禁止 AL4 依赖 `store/*`。
**第五方的判据本轮从"两条要求互相打架"扩到"要求与架构规则打架"**：前者靠读文档能发现，后者必须把 R1–R10 摆进来对照。

### ❌ 契约缺口型验收（与 AL3 同型，规模更大）

§8 旧文案里"`dim` 属性返回 2560（与配置一致）""`resolve_chain()` 输出实际生效链"这类句子——
**"与 X 一致"不是验收**（13.6 的结论）：没有可比对的两侧，也没有判定方式。
本轮把这类条目全部落成可机械判定的形式：`inspect` 两个方向的白名单断言、`request_count` 计数、链段 `source` 序列。

### ⚠️ 断言强度："单独调用某条链"的用例**挡不住** P0-10

97 个用例里，每条链都自有用例、且都通过；**但没有一条用例把两条链放在同一个 resolver 实例上按顺序调用**。
P0-10 就活在这个缝隙里。**教训（并入 §13.6 / §14.6 的判据）**：

> **"某一方单独正确"不等于"它们一起正确"。**凡存在**共享状态**（缓存、链、连接、计数器）的模块，
> 都必须有一条**跨路径的顺序用例**——否则测试覆盖的是"每个零件"，而 bug 长在"装配"上。

### ⚠️ 验收与用例的载体缺位

AL4 在 `tests/acceptance_matrix.py`（E7 的可执行载体）里**零覆盖**——AL1 已覆盖，AL2–AL5 待随逐层复核扩展。
本轮新增的"协议对齐 / 顺序回归 / 请求上界"三条**只有文字，没有可执行载体**，属同一问题的延续。

# 第八部分 · 逐层复核（DES-REV-008 · 2026-09-16）

## 16.1 AL5 结论摘要

AL5 是**唯一一层没有"业务输出"可以对照的**——它不实现记忆算法，只提供"怎么安全地跑起来"：
组合根、线程与队列、配置装载、只读投影、合规检查。这个性质决定了它的缺陷形态：

> **AL5 的 bug 不长在"逻辑算错"，而长在"断言与实现不同步"。**

16 条 P1 里有 10 条的原始形态是**恒真 / 半恒真的用例**，或**用例红在"查法"而不是"功能"**——
它们不会让任何人当场发现问题，只会让门禁"看起来在工作"。三条 P0 则都不是 AL5 内部自坏，
而是**跨层接口的失配**：

| # | 一句话 | 被破坏的上游承诺 |
|---|---|---|
| P0-12 | 离线产出（维护线程）绕过写队列直接落库；而 `stop()` 的"未完成数"只数堆深 | AL3 的**线程安全前提**（D-03 单写者）+ C3 的 drain 承诺 |
| P0-13 | 宿主线程持写事务；且用例因旧签名在第一行就 TypeError 空转 | **INV-4**（绝不阻塞宿主）+ T-AL5-09 要求 3 |
| P0-14 | 核心价值用例（V1）拿"无信号陈述"当输入，而它在 `θ_salience=0.35` 下必然过不了线 | V1 的判决建立在**恒假前提**上 |
| P0-15 | 工具路径（宿主主线程）直接 `write_now`，每写一次就**关掉 writer 的写连接**再建一条 | AL3 的**线程安全前提**（D-03 单写者）——与 P0-12 同一根因的**另一个入口** |

## 17.3 诊断期的三个坑（并入方法论）

**现象**：全量 pytest 永久挂起，且"两次卡在不同用例"。

**坑一：看门狗打了栈却看不见。** `conftest.py` 的看门狗用
`faulthandler.dump_traceback_later(..., exit=True)`，而 **pytest 默认 `--capture=fd`
会把进程退出时的输出一并吞掉**——"栈打出来了却看不见"整整误导了一轮排查。

> **判据**：任何**在进程退出之后才需要存在**的诊断输出，**都不能走被捕获的 fd**——写显式文件。

**坑二："卡点在漂移"是假象。** 第一次的输出停在管道缓冲区里没刷新，看着像卡点会变；
实际每次都是同一个用例（首个 `token_budget < 80` 的用例）。

> **判据**：**"卡点在漂移"要先怀疑观测方式，而不是先怀疑有两个 bug。**

**坑三（最有价值）：这是产品代码缺陷，不是测试环境问题。**
"pytest 又卡了"极容易被归结为测试工具（尤其它此前确实出过问题），
但**永久挂起 = 存在不终止的函数**，而测试跑的正是产品代码。

> **判据**：**"又是测试工具的问题"这个念头本身，就是最该被先证伪的那一个。**

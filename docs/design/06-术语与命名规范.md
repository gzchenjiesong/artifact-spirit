## 1. 三条约定

1. 设计文档、代码、CLI 一律使用**通用术语**（中文 + 英文并列）。
2. **「器灵 / Artifact Spirit」作为项目品牌名保留**，不参与术语统一。
3. 修仙命名（灵犀、灵台、灵识、灵纹、灵髓、灵核、元灵）**退出设计文档**，仅保留在 §4 映射表，供 README 做特色说明。

> v2.0 新增：**编号命名空间必须唯一**。同一记号（如 `L1`、`M2`、`P1`）不得在两个语义域中复用——这是 v1.0 遗留的主要缺陷，§3 给出消解方案。

## 4. 术语对照表（修仙名 ↔ 通用名）

| 修仙名 | 通用中文 | 通用英文 | 认知科学 / 业界来源 |
|---|---|---|---|
| 灵犀 | 感觉记忆 | Sensory Memory | Atkinson-Shiffrin 三存储模型（1968） |
| 灵台 | 工作记忆 | Working Memory | Baddeley 工作记忆模型（1974/2000） |
| 灵识 | 情景记忆 | Episodic Memory | Tulving 记忆分类（1972/1985） |
| 灵纹 | 语义记忆 | Semantic Memory | Tulving 记忆分类（1972/1985） |
| 灵髓 | 程序性记忆 | Procedural Memory | 认知科学通用；LangMem 同术语 |
| 灵核 | 核心记忆 | Core Memory | 业界共识（Mem0 / Letta 同术语） |
| 元灵 | 元认知 | Metacognition | 认知心理学通用；对应 Letta sleep-time |

### 4.1 「认知资产」（本项目的核心措辞）

**Agent 平台是工具，认知资产是使用者的。**

指使用者与 Agent 长期交互中沉积下来的、**关于他自己的**那一部分记忆总和：
偏好、习惯、项目背景、决策历史、关系脉络。

它**不是**"某个平台里的数据"，而是**使用者的财产**——这个区分就是 V3 的全部内容，
也是器灵存在的理由（跨 Agent 平台迁移）。

> 因此凡涉及"带走 / 迁移"的表述，一律用**认知资产**，
> 而不用"数据"或"记忆内容"——后两者都暗示它是**平台的产物**，
> 而那正是本项目要否定的前提。

## 5. 五类记忆（不是"五层"）

**记忆类型只有 5 类 + 2 柱，且不使用编号**——编号一律留给"层"（§6）：

| 类型 | 通用术语 | 时间尺度 | 职责 |
|---|---|---|---|
| 类型 | 感觉记忆（Sensory） | 秒 | 捕获输入、显著性过滤（**不落盘**，实为门控） |
| 类型 | 工作记忆（Working） | 分 | 活跃话题、推理轨迹、意图槽 |
| 类型 | 情景记忆（Episodic） | 天~月 | 会话归档、事件、决策 |
| 类型 | 语义记忆（Semantic） | 月~永久 | 去情境化事实、概念网络 |
| 类型 | 程序性记忆（Procedural） | 永久 | 技能、可复用轨迹 |
| 双柱 | 核心记忆（Core） | 恒常 | identity + soul，贯穿各层 |
| 双柱 | 元认知（Metacognition） | — | 巩固、衰减、扩散激活（跨层调度，不拥有数据） |

> **为什么去掉"五层"**：感觉记忆不落盘，本质是门口门控而非存储层；称"五层"会与架构分层（§6）的"五层"同名异义。

> **知识型记忆（Knowledge Memory）不是第六类**：由外部资料（文档 / 攻略 / 知识点）导入的积累，与语义记忆**同构**（都是去情境化的事实与概念），差异只在**来源与治理条款**——因此用 `layer="semantic"` + `type="knowledge"` 表达，**不新增类型、不新增编号**。三个术语：**知识型记忆** / **目录卡（Catalog Card）**（每条约 24 token 的极短索引描述，用于"不读正文就知道讲什么"）/ **知识通道（Knowledge Channel）**（导入 → 编目 → 检索 → 注入）。详见 [DES-RES-004](./11-知识型记忆研究与机制增补.md)。

> **程序性记忆（Procedural）的"技能 / SOP"真相在宿主**：技能以宿主的 `SKILL.md`（Agent Skills 标准）/ MCP 服务 / 工具 CLI 为载体并负责执行与生命周期，器灵**不重造 skill 系统**（对照 [DES-RES-005 §1 / §4](./12-程序性记忆与技能机制增补.md)）；器灵只保存"**何时该用哪个技能**"的**场合索引**（非主题索引）与执行中积累的**经验素材**（失败模式 / 特殊 case），且只能作为**候选**经人审后写回宿主载体，**绝不自动改写**。
>
> ⚠️ **注意"程序性记忆 ≠ 技能"**：技能是宿主侧的能力单元，程序性记忆是器灵侧的记忆类别。`skill` / `SOP` / `workflow` / 工具 / CLI / MCP 这组词的定义、中英对照与代码映射，**统一见 §11**（唯一定义处）。

## 6. 架构分层（AL1–AL5）

架构分层是**工程分层**，与记忆类型（§5）正交，编号 **`AL1`–`AL5`**（Architecture Layer）：

| 记号 | 层名 | 英文 | 职责 |
|---|---|---|---|
| **AL1** | 适配层 | Adapter | 宿主契约 ⇄ 内部 API、组合根、工具与 CLI |
| **AL2** | 核心层 | Core | 记忆领域逻辑（五类记忆 + 元认知 + 提取器），纯逻辑无 I/O |
| **AL3** | 存储层 | Storage | 持久化、检索原语、审计链 |
| **AL4** | 模型层 | Model | LLM / Embedding 协议接入、fallback |
| **AL5** | 辅助机制 | Support | 运行时、配置、可观测性、合规 |

- 详细设计文档：`layers/AL1-适配层详细设计.md` … `AL5-辅助机制详细设计.md`（编号 `LLD-AL1`–`LLD-AL5`）
- 编码任务：`T-AL1-01` … `T-AL5-xx`

## 7. 记忆详略级（L0–L2）

**`L0/L1/L2` 独占"记忆详略级"语义**（P1 首要目标），贴合"模糊印象 → 大致判断 → 回想细节"：

| 记号 | 名称 | 是什么 | 存储 |
|---|---|---|---|
| **L0** | 模糊印象 | 单条记忆的一句话摘要 | `memories.abstract` |
| **L1** | 概览 | 主题 / 实体级概览——"关于 X 我大致记得什么" | `overviews` 表（缓存） |
| **L2** | 细节 | 原文 + 来源 + 关联链 | 实时组装，不新增存储 |

> 三级**信息上层层包含**（L2 ⊃ L1 ⊃ L0）。与架构层 `AL1/AL2` 的区别：**`L`+数字=记忆级，`AL`+数字=架构层**。
>
> **依据**：分级是为了省**注意力预算**——同时在线的信息量有上限，抽象提高的是**有效容量**，因此"分级"不是"删减信息"（见 [DES-RES-003 §2](./10-神经科学依据与机制映射.md)）。

## 8. 书写约定（去歧义）

1. **架构层必须带层名或前缀**：写 `AL2 核心层`、`LLD-AL2`、`T-AL2-05`，**禁止**裸写 `L2` 表示架构层。
2. **记忆级必须带量词或语境**：写 `L1 概览`、`L0/L1/L2 三级`、`记忆 L2`，**禁止**裸写 `L1` 指向不明。
3. **编号大小写**：记号大写（`M1`、`R5`、`AL2`）；文档/决策 ID 带连字符（`D-20`、`T-AL2-05`）。
4. **"五层"仅指架构**；记忆侧一律称"五类记忆"。
5. **"核心"单独出现时指核心记忆**；指架构一律写"核心层 / AL2"。

## 10. 表述纪律（脑科学相关）

**一句话**：脑科学研究是**假设来源**与**机制候选库**，不是**正确性证明**。

本文档、LLD、编码文档、代码注释、CLI 帮助与对外文案一律遵循：

| 约定 | 内容 |
|---|---|
| ✅ **推荐表述** | **"借鉴脑科学"** / "借鉴脑科学研究"——只用于说明**来源**（如"该机制借鉴脑科学中的 X"）；能直接写量时优先写量（衰减形状、共现统计强度、注意力预算） |
| ❌ **禁用表述** | **"类脑"**、**"仿脑"**、"类脑化"、"脑启发架构"等以"像脑"为卖点的说法 |
| ❌ **禁用论证** | 以"人脑如此" / "像人一样" / "连人脑都不像"作为**立项理由、机制取舍依据或卖点**；需要论证时只能引用**可检验的结论与量**（例："重要性与频率是两个独立维度"），并给出 Agent 场景的实测判据 |

**为什么这么定**：一旦用"像不像脑"当判据，机制取舍就脱离了可测性——这正是 P4「机制既要讲得通、又要测得出」要防的**伪脑科学包装**（[DES-CHARTER §2 P4](./08-设计纲领.md)、[DES-RES-002 §5](./09-机制决策依据研究.md)）。

**逐条映射**：脑科学提供了哪些**可用的量**、每份证据的强度（A/B/C）、对应哪条机制、Agent 侧怎么量、什么条件下放弃——见 [DES-RES-003](./10-神经科学依据与机制映射.md)。

> 同一套纪律适用于**信息科学**引用（图书馆学 / 信息检索 / 个人知识管理）：一律写"**借鉴**"并给出 Agent 侧判据，不得用"图书馆都这么干"代替验证——见 [DES-RES-004 §0.3](./11-知识型记忆研究与机制增补.md)。

**v2.1 替换对照**：

| 旧表述 | 新表述 |
|---|---|
| 类脑机制 | 借鉴脑科学机制（或直接写机制名的量） |
| 类脑记忆系统 | 借鉴脑科学研究的记忆系统 |
| 类脑五类记忆 | 借鉴脑科学的五类记忆 |
| 像人一样按需回忆 | 按需回忆、逐级展开 |
| 连人脑都不像（作论据） | 与记忆研究的结论相悖 |

## 11. 程序性记忆与技能术语规范

> **v2.2 新增｜唯一定义处**。适用于任何涉及"技能 / SOP / 流程 / 工具"的设计文档、LLD、编码文档、代码标识符、CLI 帮助与对外文案。
> **为什么要单列**：`SKILL` / `SOP` / 技能 / 程序 / `procedural` / `workflow` / 工具 / CLI / MCP 这组词在中文材料里**混用且跨域**——同一个"skill"既是宿主的能力单元、又被人当成程序性记忆、还被学界当作"提示词规则"。本节给出**唯一定义 + 中英对照 + 代码映射 + 禁用对照**，消除同名异义。

### 11.1 根因：三个"域"共用了同一批词

| 域 | 谁拥有 | 涉及的词 | 器灵的立场 |
|---|---|---|---|
| **宿主域**（能力与执行） | 宿主 Agent / 工具链 | 工具 Tool、技能 Skill、SOP、工作流 Workflow、MCP、CLI | **只引用，不拥有**：不复制正文、不执行、不注册（[D-29](./12-程序性记忆与技能机制增补.md)） |
| **器灵域**（记忆与治理） | 器灵 | 程序性记忆、技能条目、场合、轨迹、案例 | **拥有**：存、检索、反馈、治理 |
| **研究域**（引用术语） | 论文 / 组织管理学 | Proceduralization、Script、Workflow(AWM)、SOP(TWI) | **只引用**：写英文原词，**不翻译成器灵实体** |

> **一句话分工**：一次"用某技能做某事"的全过程中，**宿主管"技能是什么、怎么执行"，器灵管"何时用、用得如何、哪里踩过坑"，论文管"理论上该怎么表示"。**

### 11.2 谁在哪个域（一张图）

```
┌── 宿主域：能力与执行（器灵不拥有）──────────────────────────────┐
│   工具 Tool ──▶ 技能 Skill ──▶ SOP ──▶ 工作流 Workflow           │
│   （一个函数）  （SKILL.md 目录）（技能编排）（引擎/控制流，器灵不做）│
│   附：MCP（协议）· CLI（命令行）                                 │
└────────────────────────────────────────────────────────────────┘
        ▲ 器灵只引用：存"引用 + 触发条件 + 证据"，L1/L2 是派生与缓存
┌── 器灵域：记忆与治理（器灵拥有）────────────────────────────────┐
│   程序性记忆 Procedural Memory      〔layer="procedural"〕       │
```

### 11.4 逐条定义与边界（七个最易混的点）

**① 程序性记忆 ≠ 技能。**
程序性记忆是**器灵的记忆类别**（`layer`）；技能是**宿主的能力单元**（`SKILL.md` 目录）。器灵不"存技能"，只存"技能的**记忆表示**"（技能条目）。"程序"单独出现时**无意义**——一律写"程序性记忆"或"技能条目"。

**② 技能 ≠ 技能条目。**
技能 = 宿主能执行的东西；技能条目 = 器灵对它的**引用 + 触发条件 + 证据**（`type="skill"`）。两者是**载体与记忆**的关系，不是同一物的两种叫法。所以：给宿主写 `SKILL.md` 叫"技能"；器灵库里那条记录叫"技能条目"。

**③ 技能 → SOP → 工作流 = "编排度"递增的三级**（不是同义词）。

| | 技能 Skill | SOP | 工作流 Workflow |
|---|---|---|---|
| 粒度 | **原子能力**（一件事怎么做） | **编排**（多技能/步骤的固定顺序） | **流转**（含分支、状态、角色、引擎） |
| 载体 | 一个 `SKILL.md` 目录 | 一份作业标准（可写在 `SKILL.md` 正文里） | 流程引擎 / 编排配置 |
| 器灵里的表示 | 技能条目 `type="skill"` | **同左**（SOP 是技能条目的一种内容形态，**不新增类型**） | **无对应实体**（器灵不做） |

> **判据**：提问"这需要**几件事**、有没有**固定顺序**？"——一件事 = 技能；多件事且顺序固定 = SOP；还要**分支 / 状态 / 回退 / 审批** = 工作流（超出器灵范围）。业界共识一致："工作流是**路径**，SOP 是路径上的**标准做法**，Skill 是走这条路所需的**能力**"。

**④ 工具 ≠ 技能。**
工具（Tool）是"**能调用的一个动作**"（一个函数，如 `read_file`）；技能（Skill）是"**知道何时、按什么顺序、用什么工具做成一件事**"。技能**会用到**工具；一个技能可以调用多个工具。

**⑤ 场合 ≠ 主题。**
这是器灵与知识型记忆的分野（[DES-RES-005 §1.3](./12-程序性记忆与技能机制增补.md)）：知识条目按"**主题**"索引（这条**讲什么**），技能条目按"**场合**"索引（这条**何时用**）。对应到代码：两者都写在 `abstract`，但**技能条目的 `abstract` 必须写触发条件与反例**。

**⑥ CLI / MCP / 工具 都是"宿主侧接入方式"，不是记忆类型。**
它们既不是 `layer`、也不是 `type`。器灵对外只以 `spirit_*` **工具**形态存在；`aspirit` CLI 是运维入口；MCP 服务端**不做**（[D-29](./12-程序性记忆与技能机制增补.md)）。三者一律**不进** `memories.layer` / `memories.type` 的取值域。

**⑦ 传承重建（Import）≠ 批量素材导入（Ingest）。**（2026-09-16 裁决）

| | **传承重建** Import | **批量素材导入** Ingest |
|---|---|---|
| 写进去的是什么 | `spirit_export` 产出的**档案 / 完整包**（本就是器灵的记忆） | **外部资料**（文档 / 手册 / SOP），器灵此前**不认识** |
| 与谁对称 | **`spirit_export`**（同一套格式往返保真） | **无对称端**（纯入向） |
| 语义边界 | 恢复既有记忆，逐条保真（`content_hash` 幂等） | **幂等 + 只存不编 + 记来源**，不调 LLM 理解、不摘要 |
| 名字 | `spirit_import` / `aspirit import` | `spirit_ingest` / `aspirit ingest` |

> **不采用的名**：① `spirit_learn`——承诺"理解 / 内化"，恰是 Ingest **明令不做**的事，且"学习"已被 `Hebbian 学习`（[LLD-AL2](./layers/AL2-核心层详细设计.md) M4）与"技能习得"（[DES-RES-005](./12-程序性记忆与技能机制增补.md)）占用；② `spirit_share`——方向相反（往外给 ≈ `export`）；③ `spirit_input` / `spirit_output`——**名词**，违反 §11.8(4)(5) 动词约定，且 `output` 与 `export` 重复。**"从外部获取信息"的语感属于通道名（知识通道 / 技能通道），不属于工具名。**

### 11.5 能力层级阶梯（用于判断"该不该建实体"）

```
工具 Tool          1 次调用           宿主提供   器灵只调用
  └─ 技能 Skill     1 项可复用能力      宿主提供   器灵只记"引用+触发条件"（技能条目）
       └─ SOP       多项技能的固定顺序   宿主/SOP文档 器灵以 type="skill" 表达，不新增类型
            └─ 工作流 Workflow  含分支/状态/引擎  宿主编排平台  器灵不做（无实体）
```

> **一条判据**：**凡是"编排与执行"，器灵一律不做**；器灵只在阶梯**左侧**加一列"记忆与治理"（触发条件、有效率、案例、冲突、审计）。这与 P4「不造自己用不到的东西」一致。

### 11.6 禁用 / 慎用对照

| ❌ 不写 | ✅ 写 | 原因 |
|---|---|---|
| "程序"（单称指记忆） | **程序性记忆** | "程序"与"程序性记忆"不同义，且易与"流程 / 程序代码"混 |
| "skill 层" / "技能层" | **`procedural` 层（程序性记忆）** | `skill` 是 **type**，不是 layer |
| "技能"（指代层或类型） | **技能条目**（器灵）/ **技能**（宿主） | 需先分清域（§11.1） |
| "SOP 表" / `type="sop"` | **技能条目**（`type="skill"`） | **不新增类型**；SOP 只是技能条目的内容形态 |
| "器灵的 workflow" / "工作流记忆" | **技能条目 / SOP**（视内容） | 器灵**无 workflow 实体**；workflow 仅用于引用 AWM |
| "用 skill 存技能" | **用 `type="skill"` 的技能条目存技能的引用** | 器灵不复制技能正文 |
| "工具型记忆" | **工具**（宿主）或 **技能条目**（器灵） | 工具不是记忆类型 |
| "SOP 导入 = 新功能" | **SOP 导入 = `spirit_ingest` 的一种 `type`** | 与知识型记忆**共用入口**（[DES-RES-005 §5.2 G-b](./12-程序性记忆与技能机制增补.md)） |
| "`spirit_import` = 批量导入" | **批量导入 = `spirit_ingest`**；`spirit_import` **专指传承重建** | 两者来源与对称端不同（§11.4 ⑦）。**已裁决 2026-09-16**，此前"撞名待裁决"记录作废 |

> **一句话验收**：读完一句话，能分辨它说的是**宿主的东西**、**器灵的记忆**、还是**论文的概念**——若不能，就是术语没写清。

### 11.7 与业界做法的对照

**（甲）各项目 / 规范怎么命名**（本节结论的直接依据）：

| 项目 / 规范 | 相关概念叫什么 | 载体 | 与器灵的对应 |
|---|---|---|---|
| **Agent Skills 规范**（agentskills.io） | **Skill**：`SKILL.md` 的 `name`（≤64，= 目录名）+ `description`（≤1024，写"是什么 + 何时用"），三级渐进披露（元数据 ~100 token / 正文 <5000 token / 资源按需） | 目录 + 文件 | = 器灵的「**技能**」（宿主侧）；器灵只存**技能条目** |
| **MCP**（2026-07-28 修订） | `tools` / `resources` / `prompts` 三原语，**无"技能"概念** | 宿主协议 | 器灵只**调用**；**无对应记忆实体** |
| **AWM**（ICML 2025） | **workflow**（从轨迹归纳，**自然语言、不可执行**） | 论文 / 内存 | **引用原词**；器灵**不建实体** |
| **SkillWeaver**（2025） | **skill → distill 为可执行 API** | 代码 | 印证"技能的正确形态是可执行物"——**在宿主侧** |
| **Mem<sup>p</sup>**（ACL 2026 Findings） | **Trajectory / Script / Proceduralization** | 论文 | 器灵 **L1 骨架 + L2 案例**的理论依据 |
| **LangMem / LangGraph** | **procedural memory = 提示词 / 规则 / 行为风格** | prompt | ⚠️ 与器灵 `procedural` 层**不同义**（见下方（乙）） |

**（乙）`procedural memory` 有两义，必须声明用哪一义：**

| 出处 | "程序性记忆"指什么 | 与器灵的关系 |
|---|---|---|
| **器灵 / 认知科学分类** | **技能、可复用轨迹、案例**（"我会做"） | ✅ 本文与 §5 采用这一义 |
| **LangMem / LangGraph 等框架** | **提示词 / 规则 / 行为风格**（system prompt、instructions、tool usage guidelines、workflow rules）——本质是对**提示词与行为规则的持续修订** | ⚠️ 该含义在器灵里更接近**语义 / 核心记忆**，**不是** `layer="procedural"` |

> **纪律**：引用框架文档时，若其 `procedural memory` 指"提示词规则"，**必须显式注明"（该框架义）"**，不得直接与器灵的 `procedural` 层画等号。这也是 [§10 表述纪律](#10-表述纪律脑科学相关) 在术语层面的延伸：**引用必须可追溯、可判别**。

### 11.8 代码侧命名规则

1. **层名固定 `procedural`**：写作 `layer="procedural"`，缩写 `pro`（`store/ids.py`）。**禁止** `procedure` / `skill` / `skill_layer` 作为层名。
2. **类型名固定 `skill`**：写作 `type="skill"`，须在 `common.MEMORY_TYPES` 取值域内。**禁止**新增 `sop` / `workflow` / `trajectory` 等类型——轨迹用 `episodic`+`event`，案例按其内容归 `procedural` 或 `episodic`。
3. **英文标识符**：概念词一律**小写单数**——`procedural` / `skill` / `trajectory` / `case` / `occasion` / `tool`；**禁止**用 `skills` / `SOP` / `Workflow` 作 Python 标识符或 JSON key。
4. **工具名前缀与动词约定**：器灵对外工具一律 `spirit_<verb>`（`tools/schemas.py` 现有 11 个：`spirit_recall` / `spirit_expand` / `spirit_remember` / `spirit_forget` / `spirit_restore` / `spirit_review` / `spirit_trace` / `spirit_correct` / `spirit_consolidate` / `spirit_reflect` / `spirit_export`）；**禁止**出现 `skill_*` / `mcp_*` 前缀，**禁止用名词**（`spirit_input` / `spirit_output` ❌）。已规划未落码的三个：`spirit_soul`（M4）/ `spirit_import`（**传承重建**，对称 `spirit_export`，V3·M3）/ `spirit_ingest`（**批量素材导入**，D-27 提案，M3）。
   - ✅ **撞名已裁决（2026-09-16）**：`spirit_import` 与批量导入入口**不再同名**——前者专指传承重建，后者改名 **`spirit_ingest`**（工具 + CLI `aspirit ingest` 都给）；**禁用** `spirit_learn` / `spirit_share`（理由见 §11.4 ⑦）。
5. **CLI 子命令**：一律 `aspirit <verb>`；技能相关只做**记忆侧**动作（摄入 `ingest` / 检索 / 审查 / 导出），**禁止**出现"执行技能 / 运行 SOP"类子命令。
6. **文档并列写法**：首次出现用"**中文（English）**"，此后中文即可；引用论文原词时**保留英文**（如 `Proceduralization`、AWM 的 `workflow`）。

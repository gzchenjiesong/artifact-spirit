# 器灵 / Artifact Spirit — 底层存储选型分析

> 决策记录（ADR-002）
> 日期：2026-09-14（2026-09-15 修订：移除已废弃外部组件相关分析，结论不变）
> 状态：**已定**（接口与建表的最终形态见 [LLD-AL3 存储层详细设计 §2 / §5](./layers/AL3-存储层详细设计.md)，本文为选型依据）
> 结论：**默认且唯一后端 = SQLite + sqlite-vec**（依赖全为 public domain / MIT / Apache-2.0）；保留 `MemoryBackend` 抽象，供未来后端接入（准入线见 [ADR-001](./01-开源许可决策与合规约束.md)）。

---

## 1. 结论

| 问题 | 答案 |
|---|---|
| 底座用什么？ | **SQLite**（标准库自带）+ **sqlite-vec**（零依赖向量检索扩展） |
| 为什么不基于成熟记忆框架构建？ | 它们的核心价值（**记忆提取 / 分层摘要 / 记忆编排**）正是器灵要自研的东西；拿来当底座，等于用一个记忆系统实现另一个记忆系统（§4.1） |
| 协议上是否干净？ | 是。SQLite 为 public domain，sqlite-vec 为 MIT / Apache-2.0，**可直接 import，无需进程隔离** |
| 后端要可插拔吗？ | 要。`MemoryBackend` 抽象 + `SQLiteBackend`（默认）。**MVP 只实现这一个**；未来后端必须先过 ADR-001 的许可准入 |
| 部署依赖？ | **零服务**：单文件数据库，无守护进程、无端口、无外部引擎 |

## 2. 能力栈拆解（为什么要"自研编排层"）

一个完整的记忆系统是**三层叠加**：

| 层 | 内容 | 器灵的来源 | 状态 |
|---|---|---|---|
| **存储层** | 关系数据、文本本体、时间与来源字段 | SQLite | ✅ 已定 |
| **检索层** | 向量检索 / 关键词检索 / 融合排序 | sqlite-vec + BM25（FTS5） | ✅ 已定 |
| **编排层** | 记忆提取、分层摘要（L0/L1/L2）、会话归档、巩固 / 衰减 / 扩散激活、去重与治理 | **器灵自研** | 🟡 核心价值所在 |

关键认知：**下两层是可被现成组件干净替代的"商品"，最上层的"编排"才是器灵存在的意义** —— 它不该依赖任何外部记忆产品。

## 3. 候选对比

| 候选 | 真实定位 | 协议 | 与器灵关系 | 备注 |
|---|---|---|---|---|
| **SQLite** | 纯关系存储 | public domain | ✅ **底层存储** | 无向量能力，需扩展 |
| **sqlite-vec** | 向量检索原语（SQLite 扩展） | MIT / Apache-2.0 | ✅ **底层检索** | 纯 C 单文件、零依赖、跨平台含 WASM |
| **Mem0** | 完整记忆层（提取 + 检索） | Apache-2.0（open-core） | ⚠️ **参考对象，不是依赖** | 图记忆 / consolidation 在付费版；单厂商 relicense 风险 |
| **Graphiti / Zep** | 时序知识图谱记忆 | Apache-2.0 | ⚠️ **参考对象** | 需图数据库服务，违背"零服务" |
| **Letta / LangMem** | Agent 记忆运行时 / 记忆库 | Apache-2.0 | ⚠️ **参考对象** | 离线巩固思路可借鉴 |
| 托管向量库（Qdrant / Milvus 等） | 专用向量服务 | Apache-2.0 / 混合 | 🔒 **暂不引入** | 器灵量级不需要；逼近百万级再评估 |

> 这些项目的**设计思路**在 [RES-001 记忆质量调研](./03-记忆质量调研.md) 中系统吸收，但**不作为依赖**：器灵只需要它们的结论，不需要它们的运行时。

## 4. 三个关键判断

### 4.1 成熟记忆框架是参考对象，不是底层

它们的能力（事实抽取、多信号检索、时间推理、离线巩固）与器灵的「借鉴脑科学的记忆编排」**高度重叠**。拿它当底层，等于用一个记忆系统实现另一个记忆系统。此外：

- open-core：图记忆、dream consolidation 等高级能力在付费版
- 单厂商 + 融资背景，有 MongoDB（AGPL→SSPL）、Grafana（Apache→AGPL）式的 relicense 前科
- 自托管常需 Postgres + 向量库（+ 可选图库），并非单文件

结论：**只作参考对象，不作依赖。** 器灵取它们的"结论"，不取它们的"运行时"。

### 4.2 sqlite-vec 对器灵量级够用

- 当前稳定版为暴力扫描（无 ANN），但 **Agent 记忆是几十万条以内的场景**，此量级暴力扫描是"完美召回 + 零索引维护"的低维护最优解
- 支持 binary quantization（约 32x 压缩、10x 提速）与 Matryoshka 截断
- ANN 索引仍在 alpha，非生产级，但器灵暂不需要
- 迁移信号明确：当记忆量逼近百万级、高 QPS、需横向扩展时，再评估托管向量库

### 4.3 "自研编排层"是定位红利，不是额外成本

- 引入成熟记忆框架：器灵只做**上层编排**（巩固 / 衰减 / 扩散激活），提取与摘要白拿——但编排层仍要自己写，且白拿的部分无法按"注意力预算"改造
- 用 SQLite：器灵做**全栈编排**（连提取 / 摘要一起），彻底摆脱服务依赖与许可负担
- 前者省工作量，后者省合规与运维。**器灵选后者**，因为"提取与分层是否服务于注意力预算"本身就是差异化设计点，外包出去反而失去主导权

## 5. 推荐架构：Backend 抽象 + 单实现

```
artifact_spirit/
└── store/
    ├── base.py           # MemoryBackend 抽象接口（核心 MIT）
    └── sqlite_backend.py # 默认且唯一实现：SQLite + sqlite-vec，零部署
```

### 5.1 原则

1. **核心编排逻辑（五类记忆 + 元认知）全部位于器灵核心层（MIT），不 import 任何后端特有代码**
2. 编排层只依赖 `MemoryBackend` 接口，后端可插拔
3. 默认后端 `SQLiteBackend` **开箱即用**：用户无需安装任何服务
4. 未来若引入外部服务型后端，必须走 extra 包 + 遵守 ADR-001 的三条硬约束（进程隔离、不 import、不 vendor）

### 5.2 接口草案

> ⚠️ 以下为选型期的**草案**（用于说明抽象边界）。**签名级最终契约已固化于 [LLD-AL3 存储层详细设计 §2.2](./layers/AL3-存储层详细设计.md)**，编码以那份为准。

```python
class MemoryBackend(Protocol):
    def store(self, layer: str, uri: str, content: str, meta: dict) -> None: ...
    def read(self, uri: str, level: str = "full") -> str: ...
    def find(self, query: str, layer: str, top_k: int = 8) -> list[Hit]: ...
    def delete(self, uri: str) -> None: ...
    def link(self, uri_a: str, uri_b: str, weight: float) -> None: ...
    def list(self, layer: str) -> list[str]: ...
    def snapshot(self) -> bytes: ...   # 器灵传承（导出/导入）
```

## 6. 协议影响

| 路径 | 器灵协议 | 能否 import | 部署 |
|---|---|---|---|
| `SQLiteBackend`（默认且唯一） | MIT ✅ | 可 import 一切 | 零服务、单文件 |
| 未来的外部服务型后端（可选 extra） | MIT ✅（进程隔离） | **禁止 import 其官方包** | 需常驻服务，且过 ADR-001 准入 |

本方案的收益是**把许可焦虑从根上消除**：默认路径不含任何 copyleft 组件，也不需要"靠自律守着隔离"——因为根本不需要隔离。

| 阶段 | 后端 | 理由 |

## 7.5 失去清单与权衡（自研全栈的代价）

不基于成熟记忆框架构建并非无代价。失去的能力分三级，只有第一级是需要正视的真代价：

### 真失去（需正视）

1. **验证过的提取 / 检索质量**：业界成熟方案有公开 benchmark 数字（见 [RES-001](./03-记忆质量调研.md)）与大规模调优过的 prompt、去重阈值。器灵自研的提取与召回效果**是未知的**，prompt 工程、去重阈值、融合权重都要从零标定。
2. **现成的分层摘要管线**：L0/L1/L2 的自动生成需要器灵自研摘要 prompt 与异步生成管线。
3. **现成的"意图分析 + rerank"检索范式**：器灵的检索是**多因子融合召回**（语义 + 活性 + 扩散 + 实体 + 时间 + 核心记忆），没有 LLM 意图分析与 rerank 兜底——需自己调到可用。

### 本来就要做（只是从"白拿"变自研）

记忆提取、会话归档、巩固 / 衰减 / 扩散激活 —— 这三件本来就是器灵的定位。基于成熟框架时是"先让它提取一遍、再自己分层"，属重复劳动；现在只是把"提取 prompt"也纳入自研，与核心价值同一条生产线。

### 本不需要（不算损失）

多模态解析、多租户 / 权限、资源导入、外部向量引擎 —— 器灵聚焦纯文本记忆与单用户场景，这些重型能力本来就用不上，失去是减负而非损失。

### 辩证：反向收获

自主可控（不依赖任何外部产品走向与 relicense 决策）、零服务依赖、协议彻底干净、整体更轻。

### 判断

**结论：值得，但须把「提取 / 召回质量自研」列为项目主要风险与投入，不可轻描淡写。** 质量风险已通过 [RES-001 记忆质量调研](./03-记忆质量调研.md) 收敛——无需从零造，可借鉴业界已验证范式：结构化提取、多信号检索打分、离线巩固、轻量时序图。

## 7.6 可读性与可评审性澄清

一个易被混淆的点：**「SQLite = 向量化、不可读」是误解**。可读性来自「记忆本体」，本体与索引必须分离：

- **记忆本体** = 结构化数据（`memories` 表）+ 按需导出的文本投影，人类可读，是事实来源
- **记忆索引** = 向量 / BM25 / 图，机器可读，是检索加速结构

**由此立一条硬约束（2026-09-14 修订）**：**结构化数据是单一真相源，文本是按需导出的投影**，无需实时维持 markdown 文件。读写分离——写走结构化 API（+ append-only audit 事件），读 / 审计走按需导出。

### 修订说明：单一真相源 + 按需投影

原约束「记忆本体必须存 markdown/JSON 文本」过度保守，会带来高频写文本、双向同步、格式破坏的弊端。修正为投影模式：

1. **真相源 = 结构化数据**（`memories` 表 + 旁挂向量索引），不是文本文件
2. **文本 = 按需导出投影**（`export()` = 查询 + 渲染，纯函数、实时、单向映射），无「文本 ↔ 结构化」反向同步
3. **读写频率不对称**：写（update / merge / decay / 巩固）高频，读（审计 / 评审）低频——不必为低频读维持高频写的文本
4. **可读 ≠ 可溯**：可读 = 查当前状态投影；可溯 = append-only `audit` 事件表（op / before / after / reason / ts）回放历史
5. **明确取舍**：放弃「文本直改生效」，换取「结构化单一真相源」的简洁

这条直接简化 `SQLiteBackend`：真相源 = 结构化表，`export` / `status` / `layers` 均为纯查询 + 渲染，无冗余文本存储。

> **可观测层是器灵的差异化核心，不是选型附属品。** 器灵要求解释"为什么遗忘 / 为什么召回这条 / 印象如何巩固成信念"，因此审计与可读视图必须自建，不能外包给任何底座。

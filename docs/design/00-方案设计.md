## 1. 项目目标

### 1.1 设计目标的来源（两档，主次分明）

器灵的目标分两档。这个区分很重要：**借鉴脑科学机制是"追加"目标——用来补全前一档做不到的事，不是全部。**

> **P1 的来源（为什么是分级抽象）**：LLM 的上下文是**稀缺资源**——贵、会被无关内容稀释、长了还会"中间遗忘"。人类同样受这条约束：注意与工作记忆容量极为有限，因此采取「先有模糊印象 → 再做大致判断 → 需要时才回想细节」的**按需提取**策略。器灵把这一结构工程化：**L0 印象 / L1 概览 / L2 细节**三级组织，召回逐级展开，而不是一次性灌入全文（依据见 [DES-RES-003 §2.1](./10-神经科学依据与机制映射.md)）。
> **P2 的来源（为什么必须可查看 / 可审查 / 可跟踪）**：运行一段时间后要能逐条复盘 Agent 究竟记住了什么，才谈得上主动干预优化；人类可读对调试的意义是数量级的。
> 这两点**由器灵自己实现**（不依赖任何外部记忆产品）。A 档（五类记忆等）是在此之上**追加**的设计目标。

**P 档：首要目标（原始动因，必须自主实现）**

| # | 目标 | 可检验的表述 |
|---|---|---|
| **P1** | **分级记忆 L0/L1/L2** | 记忆按"模糊印象 → 大致判断 → 细节回想"三级组织；召回时逐级展开，而非一次性灌入全文 |
| **P2** | **可查看 / 可审查 / 可跟踪** | 运行后可逐条查看"Agent 记住了什么"，含来源、时间、置信度、变更史；可主动干预 |
| **P3** | **记忆资产可迁移** | 记忆可完整导出为**开放、人类可读**的格式，不依赖器灵运行时；换工具不归零 |

**A 档：追加目标（补全 P 档做不到的）**

| # | 目标 | 可检验的表述 |
|---|---|---|
| **A1** | **会记**，而不只是能用 | 记忆按时间尺度分层递进（感觉→工作→情景→语义→程序） |
| **A2** | **有取舍** | 写入前判断显著性；长期不用则**降权并退出自动召回**（不删除） |
| **A3** | **会沉淀** | 情景在跨会话复现后提升为语义，高复用模式固化为程序性记忆 |
| **A4** | **有自我** | 核心记忆（identity/soul）让记忆保持一致的人格表征 |
| **A5** | **可逐层落地**（工程目标） | 每个分层都能独立开发、独立测试、独立验收，再整体集成 |

> **读法**：P 档决定"这个项目为什么存在"，A 档决定"它比一个分级存储好在哪"。任何取舍冲突时，**P 档优先**。

### 1.2 非目标（明确不做）

| 非目标 | 理由 |
|---|---|
| 多用户 / 多租户 / 权限体系 | 聚焦单用户 Hermes 场景 |
| 多模态记忆（图像 / 音频） | 聚焦纯文本；VL embedding 因此不选 |
| 通用上下文数据库 | 只服务自己的宿主 Agent，不做通用存储产品 |
| 图数据库依赖 | 用 SQLite 自建轻量时序图，拒绝 Neo4j/FalkorDB 类服务依赖 |
| 前端 UI | 通过 CLI 与 `system_prompt_block` 暴露状态，不做独立界面 |
| **MVP 不做 `MERGE` / `INVALIDATE` / `FORGET` 三个去重态** | 后三者依赖时态与衰减模型（M3）；MVP 只做 `ADD` / `UPDATE` / `IGNORE`。**这是主动分期，非遗漏**（[DES-REV-001 §3.6](./07-设计评审.md)） |
| **MVP 不做双时态语义查询（as-of）** | `valid_from` / `valid_to` 字段**预留**，但 MVP 无写入 `valid_to` 的路径（写它的是 `INVALIDATE`）。语义随 M3 一起启用（[DES-REV-001 §3.3](./07-设计评审.md)） |
| **不锁定任何私有记忆格式** | P3 是首要目标——"换工具记忆归零"正是我们要解决的问题，不能自己成为新的锁定方 |
| **不做 skill 运行时 / 工作流引擎** | 技能与 SOP 的**真相在宿主载体**（Agent 的 skill 目录 / MCP / 工具 CLI），宿主负责执行与生命周期；器灵只负责"**何时该用哪个技能**"的场合索引与经验素材积累，不重造调度与执行（[DES-RES-005 §1 / §4](./12-程序性记忆与技能机制增补.md)） |

### 1.3 一句话定位

器灵是 **Hermes Agent 的 Memory Provider 插件**，默认以 **SQLite + sqlite-vec** 为底座（零服务、零部署），在其之上实现借鉴脑科学的**多层记忆编排层**；后端接口可插拔，未来若要接入外部服务型后端，须先通过 [ADR-001](./01-开源许可决策与合规约束.md) 的许可准入。

宿主自带的记忆能力解决"**能用**"；器灵解决"**会记**"、"**记得对**"、"**记得住且带得走**"。二者是层级关系，非替代关系。

### 1.4 核心价值（三条）

这三条是器灵存在的理由，也是与"向量库 + RAG"方案的**根本分野**。

| # | 核心价值 | 对用户意味着什么 | 对应目标 |
|---|---|---|---|
| **V1** | **按需回忆、逐级展开** | 不把几十年的记忆一次性塞进上下文；先给"模糊印象"，需要时才逐级展开细节——**既是渐进披露的检索范式，也省 LLM 的注意力** | P1 |
| **V2** | **记忆是可见、可审、可干预的** | 能一条条看到 Agent 究竟记住了什么，能追溯它从哪来、什么时候改的——**这是复盘的机制，也是主动优化的入口**。相比黑盒向量，人类可读对调试的意义是数量级的 | P2 |
| **V3** | **记忆是资产，不属于工具** | 个人记忆是几十年的认知资产。**换一个 Agent 平台就记忆归零，是当前大量 AI 使用者的真实痛点**。器灵必须保证记忆可完整带走 | P3 |

> **V3 的工程含义**：导出格式必须**开放 + 人类可读 + 不依赖器灵运行时**。一个只存在于 SQLite 二进制里的记忆，等于没有记忆资产。
>
> **V1 与 V2 的关系**：V1 解决"怎么高效地用记忆"，V2 解决"怎么信任和修正记忆"。二者共同构成"可用的长期记忆"——只有 V1 会变成不可信的黑盒，只有 V2 会变成昂贵的全量检索。

## 2. 核心机制总览

### 2.1 记忆结构：五类记忆 + 双柱

| 记忆类型 | 时间尺度 | 职责 |
|---|---|---|
| 感觉记忆 | 秒 | 捕获原始输入，显著性过滤；**噪声不落盘** |
| 工作记忆 | 分 | 会话活跃话题分组、意图槽；容量上限 4±1 组块 |
| 情景记忆 | 天~月 | 一次会话 = 一段经历，带时空上下文 |
| 语义记忆 | 月~永久 | 去情境化的概念、事实、偏好、实体 |
| 程序性记忆 | 永久 | 技能、可复用轨迹、经验模式 |

**双柱（纵贯五类记忆，不是第六、第七类）**：

- **核心记忆**：器灵本体（identity / soul）。**这是"器灵"之名的由来。**
- **元认知**：跨层调度器，**不拥有数据**，只操作数据（巩固 / 衰减 / 扩散激活 / 健康度）。

### 2.2 首要机制（P 档）

| 机制 | 一句话 | 详见 |
|---|---|---|
| **分级加载 L0/L1/L2** | 记忆按"模糊印象 → 大致判断 → 细节回想"三级组织；召回逐级展开，按需加载，而非一次性灌入全文 | [LLD-AL2 §5 M9](./layers/AL2-核心层详细设计.md) |
| **审查、溯源与主动干预** | 能逐条看到"记住了什么"、它从哪来、何时被改；用户可修正 / 降级 / 删除 | [LLD-AL2 §5 M11](./layers/AL2-核心层详细设计.md) |
| **记忆资产导出** | 完整导出为开放、人类可读的格式，不依赖器灵运行时 | [LLD-AL3 §5 M10](./layers/AL3-存储层详细设计.md) |

### 2.3 追加机制（A 档）

| 机制 | 作用位置 | 一句话 | 详见 |
|---|---|---|---|
| **显著性过滤** | 感觉记忆门口 | 零 LLM 启发式打分，决定"值不值得记" | [LLD-AL2 §5 M1](./layers/AL2-核心层详细设计.md) |
| **巩固提升** | 元认知 | 工作→情景→语义→程序 的单向递进流水线 | [LLD-AL2 §5 M2](./layers/AL2-核心层详细设计.md) |
| **衰减排序与降级** | 元认知 | 衰减**只作排序信号**；`dormant` = 只保留 L0 参与召回；**删除仅两个入口且可恢复** | [LLD-AL2 §5 M3](./layers/AL2-核心层详细设计.md) |
| **关联激活** | 元认知 | Hebbian 共激活建边 + 扩散激活召回 | [LLD-AL2 §5 M4](./layers/AL2-核心层详细设计.md) |
| **多因子融合召回** | 元认知 | 语义 + 活性 + 扩散 + 时间 + 核心一致性 + 实体匹配 加权融合 | [LLD-AL2 §5 M5](./layers/AL2-核心层详细设计.md) |
| **记忆进化**（M4） | 元认知 | 新记忆入库时，触发相邻记忆的摘要与关联更新（Zettelkasten 式） | [LLD-AL2 §5 M10](./layers/AL2-核心层详细设计.md) |

> 融合打分本质是斯坦福 generative agents 的 `relevance + recency + importance` 的器灵化扩展（RES-001 §3）。

## 3. 分层架构

### 3.1 五层结构

```
┌───────────────────────────────────────────────────────────────┐
│  AL1  适配层  Adapter                                          │
│      宿主契约 ⇄ 内部 API ｜ 工具与 CLI 入口                      │
├───────────────────────────────────────────────────────────────┤
│  AL2  核心层  Core                                             │
│      记忆领域逻辑：五类记忆 + 元认知 + 提取器（纯逻辑，无 I/O）        │
├───────────────────────────────┬───────────────────────────────┤
│  AL3  存储层  Storage           │  AL4  模型层  Model             │
│      持久化 + 检索原语 + 审计   │  LLM / Embedding 接入          │
├───────────────────────────────┴───────────────────────────────┤
│  AL5  辅助机制  Support（横向支撑，被各层使用）                  │
│      运行时（组合根/线程/队列）· 配置 · 可观测性 · 合规           │
├───────────────────────────────────────────────────────────────┤
│  共享内核  Shared Kernel（零 I/O、零包内依赖，各层皆可依赖）        │
│      common.py（纯函数）· config_schema.py（声明式配置契约）       │
└───────────────────────────────────────────────────────────────┘
```

> **组合根在 AL5，不在 AL1**：`runtime/lifecycle.py` 是装配依赖的地方（DI 容器），
> 它是 AL5 中**唯一**允许 import 各层具体实现的位置。AL1 的 `provider.initialize()`
> 只是调用方（见 §4.1）。

### 3.2 各层功能范围

| 层 | 包含模块 | 负责 | **不负责** |
|---|---|---|---|
| **AL1 适配层** | `provider.py`、`cli.py`、`tools/` | 宿主契约适配、工具注册、CLI、错误转换 | 记忆算法、存储实现、HTTP 协议细节、**依赖装配**（属 AL5 组合根） |
| **AL2 核心层** | `core/`（layers / metacognition / consolidation / decay / activation / salience / recall）、`extract/` | 五类记忆语义、元认知调度、提取与去重决策 | 落库、网络调用、线程管理、具体 SQL |
| **AL3 存储层** | `store/`（base / probe / schema.sql / sqlite_backend / text / ids / archive / reindex） | 真相源持久化、检索原语、审计链、重嵌入与重放、**记忆包导入/导出** | 记忆语义（何时写、写什么） |
| **AL4 模型层** | `model/`（base / openai_compat / resolver） | 协议调用（OpenAI 兼容）、重试、fallback 链 | 提示词内容、记忆逻辑、成本决策、**网络探活**（INV-5） |
| **AL5 辅助机制** | `runtime/`（**lifecycle 组合根** / writer / maintenance / events / threading_ / timeout）、`config/`、`observability/`、`compliance/` | 依赖装配（**组合根**）、线程与队列、配置装载、状态报告、合规 CI | 任何业务规则 |
| **共享内核** | `common.py`、`config_schema.py` | 纯函数工具、声明式配置契约（**零 I/O、零包内依赖**） | 任何层特定逻辑；任何状态 |

### 3.3 为什么是这五层

| 分层依据 | 说明 |
|---|---|
| **可替换性** | AL3/AL4 是"外部世界边界"——换存储或换模型厂商不应触及其他层，故独立成层 |
| **可测试性** | AL2 无 I/O，可用纯内存 fake 完整单测；AL5 的队列可用 fake backend 单测 |
| **变更频率** | AL1 随宿主契约变、AL4 随模型厂商变、AL2 随产品语义变——三者节奏不同，故分离 |
| **复用性** | AL4（模型层）不依赖任何宿主；未来支持 OpenClaw 等宿主时可原样复用 |

> **为什么拆出 AL4 模型层**：ADR-003 的模型方案（三档分层 + fallback 链 + 交叉验证）体量已足够独立，且它有独立的替换动因（换网关 / 换厂商）。若并入 AL5，会让"辅助机制"承担两种完全不同的变更原因。

## 4. 层间依赖与协作

### 4.1 允许的依赖方向（单向）

```
AL1 适配层 ──▶ AL2 核心层 ──▶ AL3 存储层（仅协议）
   │              │      └─▶ AL4 模型层（仅协议）
   │              │
   └──────────────┴──▶ AL5 辅助机制（横向支撑）

AL3 ⟂ AL4    （互不依赖，同层并列）
AL5 ⟂ 业务   （不依赖任何业务层；唯一例外：组合根 runtime/lifecycle.py）
```

> **组合根例外要写在规则里，不能靠"整层放行"**：`runtime/lifecycle.py` 必须 import
> 各层具体实现才能完成装配。把例外精确到一个文件（R10），AL5 的其余部分
> （writer / maintenance / config / observability）就仍然要守边界。

### 4.2 禁止的依赖（硬规则，违反即返工）

| # | 规则 | 理由 |
|---|---|---|
| **R1** | `core/*`、`extract/*` **只能**依赖 `store/base.py`、`model/base.py` 等协议与共享内核，其余一律越界 | 编排与后端解耦，可单测 |
| **R2** | `store/*` **禁止**依赖 `core/*`、`extract/*`、`model/*` | 存储不知道编排 |
| **R3** | `model/*` **禁止**依赖 `core/*`、`store/*`；且**不得引入 `openai` SDK** | 模型层只做协议转换，HTTP 细节不外泄 |
| **R4** | **只有 `provider.py`** 可依赖宿主（Hermes）代码，其余位置一律禁止 | 宿主适配收敛为一处；`provider.py` 的豁免是规则的**目的**，不是例外 |
| **R5** | `core/*`、`extract/*` **禁止**出现 `httpx` / `sqlite3` / `openai` 等 I/O 库 | 纯逻辑，便于测试与移植 |
| **R6** | `__init__.py` 只做 `register()`，零业务逻辑 | 入口稳定 |
| **R7** | 任何位置**禁止**引入传染性许可 / 许可不明的依赖（清单按许可类别维护） | [ADR-001](./01-开源许可决策与合规约束.md) 许可准入 |
| **R8** | 只有 `runtime/*` 可创建线程，也只有它能用并发/异步原语 | 并发模型收敛 |
| **R9** | **层内实现模块不可跨层**：`store.sqlite_backend`、`model.resolver`、`model.openai_compat` 只在所属包内可见 | 否则最外层会把 sqlite-vec、httpx 一起拖进来，实现细节变成事实上的公开 API |
| **R10** | **AL5 不得依赖业务层实现**（只准依赖协议与共享内核）；唯一例外是组合根 `runtime/lifecycle.py` | AL5 是"横向支撑"，没有边界的支撑层会退化成第二套业务实现入口 |

> CI 固化：自研检查器 `compliance/arch_rules.py`（`pytest tests/test_arch.py`、
> `aspirit layers --check`）守 R1–R6、R8–R10；依赖扫描守 R7。
> **R1–R10 的规则表与代码是同一份真相**：规则改动必须同时改 `arch_rules.py` 与本表（DES-REV-003）。

### 4.3 层间协作契约

**层与层只通过两类东西交互**：

| 交互物 | 形态 | 举例 |
|---|---|---|
| **协议**（跨层主通道） | `typing.Protocol` + 数据类 | `MemoryBackend`、`LLMProvider`、`LayerService` |
| **事件**（异步通道） | 投递到 AL5 队列的任务对象 | `TurnEvent`、`ExtractTask`、`CommitTask` |

**禁止**：跨层直接访问对方的私有实现、跨层共享可变全局状态、跨层回调穿透（如 AL3 回调 AL2）。

### 4.4 关键协作时序（概览）

```
[Hermes]  prefetch ──▶ AL1 ──▶ AL2 召回引擎 ──▶ AL3.vector/keyword_search
                                    │                AL4.embed(query)
                                    └─▶ 融合 → 裁剪 → 返回文本

[Hermes]  sync_turn ─▶ AL1 投递事件 ─▶ AL5.writer 队列（立即返回）
                                        └─▶ AL2 显著性打分 ─▶ AL5 提取队列 ─▶ AL2 提取 ─▶ AL3 落库

[Hermes]  on_session_end ─▶ AL1 投递 ─▶ AL5.maintenance（离线巩固）
```

> 细节时序见 [LLD-AL1 §5 M4/M5](./layers/AL1-适配层详细设计.md) / [LLD-AL2 §5 M5](./layers/AL2-核心层详细设计.md) / [LLD-AL5 §5 M1–M2](./layers/AL5-辅助机制详细设计.md)。

## 5. 各层核心要点与制约

### AL1 适配层 [详细设计 →](./layers/AL1-适配层详细设计.md)

**要点**：实现 MemoryProvider 全契约；`is_available` 本地判定；`initialize` 调起 AL5 组合根完成装配；工具注册与 CLI 入口。

**制约**：

- `is_available()` **禁止网络调用**（Hermes 硬要求）
- `sync_turn` / `on_session_end` **必须非阻塞**（投递即返回）
- `prefetch` **同步且有超时护栏**（超时返回核心记忆摘要保底）
- 密钥**永不落配置文件**，只走环境变量
- 所有路径基于 `hermes_home`，禁止硬编码 `~/.hermes`

### AL2 核心层 [详细设计 →](./layers/AL2-核心层详细设计.md)

**要点**：五类记忆服务 + 元认知调度 + 提取器（结构化 schema + 六态更新决策）。

**制约**：

- **纯逻辑**：不得出现任何 I/O 库（R5），只依赖协议
- 元认知**不持有数据**，只调度
- 层间递进**单向**：不出现逆向搬移；"降级"只改 `status`
- 巩固/衰减**在离线后台执行**，不在在线热路径
- 提取输出必须过 schema 校验；失败重试 1 次后降级为"仅存原文"

### AL3 存储层 [详细设计 →](./layers/AL3-存储层详细设计.md)

**要点**：`MemoryBackend` 协议 + SQLite 实现 + 完整 DDL + 审计链 + 重嵌入/重放工具。

**制约**：

- **结构化数据是单一真相源**；文本是按需导出的纯函数投影，**永不反向同步**
- `audit` 表 **append-only**，永不 UPDATE/DELETE
- 派生字段（`strength` / `access_count` / `last_access_at`）**必须可从 `audit` 重放重建**
- 写入与索引（`memories` + `vec` + `fts` + `audit`）**同事务提交**
- 检索只读，不加写锁

### AL4 模型层 [详细设计 →](./layers/AL4-模型层详细设计.md)

**要点**：OpenAI 兼容 httpx 客户端；三档模型解析；fallback 链。

**制约**：

- **embedding 不可 fallback 到 LLM**；未配置时降级 BM25
- 只实现 **OpenAI 兼容协议**一套代码，不绑死厂商
- 写入与检索**必须同一 embedding 模型**（与 AL3 的 `meta` 校验联动）
- 非 JSON 输出：加 schema 提示重试 1 次，仍失败抛错交由 AL2 降级
- 配置里只存 `api_key_env`（变量名），不存 key

### AL5 辅助机制 [详细设计 →](./layers/AL5-辅助机制详细设计.md)

**要点**：**组合根**（`lifecycle.py`，装配全部依赖的唯一位置）+ writer / maintenance 线程与队列；配置装载与校验；状态与审计视图；合规 CI。

**制约**：

- **组合根在本层**：`runtime/lifecycle.py` 是唯一可 import 各层具体实现的位置（R10 的显式例外）
- 写操作**单写者串行化**，从根本消除 `SQLITE_BUSY`
- 是**唯一可创建线程**的层（R8），也是唯一可用并发/异步原语的层
- 队列溢出时按优先级丢弃（保记忆写入、弃摘要）；优先级是**穷举表**，未知任务类型直接抛错而非静默降档
- 启动时校验 `embedding_model` 与库中记录一致，不一致拒绝启动
- 崩溃后提供 `replay` 重建派生字段、`reindex` 重建向量

## 6. 实现要求（跨层硬约束）

以下 14 条**不可违反**。它们跨层生效，故写在概要设计；具体验证方式在各层详细设计中落实。

| # | 不变量 | 违反后果 |
|---|---|---|
| **INV-1** | 单一真相源：结构化数据是唯一真相；文本是纯函数投影，永不反向同步 | 双向同步破坏一致性 |
| **INV-2** | 写入 = 检索同一 embedding 模型与维度 | 向量空间不对齐，检索全废 |
| **INV-3** | 核心编排不依赖具体后端（只认 Protocol） | 后端可插拔失效 |
| **INV-4** | `sync_turn` / `on_session_end` 非阻塞 | 拖慢宿主主循环 |
| **INV-5** | `is_available()` 禁止网络调用 | 违反 Hermes 契约 |
| **INV-6** | embedding 不可 fallback 到 LLM | 行为错误 |
| **INV-7** | **删除仅两个入口**（① 记忆优化任务判定"错误 / 冲突 / 不可达" ② 用户显式要求）；**请求本身可审计**；**默认保留快照因而可恢复**（合规删除除外） | 时间/频率驱动的删除会系统性淘汰"低频但关键"的记忆；静默删除不可接受 |
| **INV-8** | `audit` 表 append-only | 审计链断裂 |
| **INV-9** | 所有路径基于 `hermes_home` | 存储隔离失效 |
| **INV-10** | 禁止引入传染性许可（AGPL / SSPL）或许可不明的依赖 | 许可传染不可逆 |
| **INV-11** | 核心记忆更新高门槛低频（M3+ 须交叉验证） | 人格被噪声污染 |
| **INV-12** | 派生字段可从 `audit` 重放重建 | 崩溃后状态不可恢复 |
| **INV-13** | **记忆资产可完整、无损导出为开放且人类可读的格式**（内容 / 层 / 时间 / 置信度 / 关联），该格式**不依赖器灵运行时**即可阅读 | 记忆被锁死在工具里——正是 P3 要解决的痛点，不能自己成为新的锁定方 |
| **INV-14** | **记忆包往返幂等**：依 `content_hash`（内容寻址指纹）判定，`import` 重复执行**不产生重复记忆**，`export → import → export` 等价 | 往返不幂等则去重失效、关联断裂——G2（自由迁移）落空 |

## 7. 验收策略

### 7.1 分层单独验收

每层必须能**脱离其他层独立测试**。手段：为下层依赖提供 fake。

| 层 | 独立测试手段 | 验收信号 |
|---|---|---|
| AL1 | 用 **fake 核心层**（返回固定召回结果）驱动 | 契约方法全部按语义返回；非阻塞断言通过 |
| AL2 | 用 **内存 fake backend + fake model** | 五类记忆/四机制的算法行为可断言；无 I/O 调用 |
| AL3 | 用**临时 SQLite 文件** | DDL 可建；CRUD/检索/审计/重放可断言 |
| AL4 | 用**本地 mock HTTP**（不依赖真实网关） | 协议转换、重试、fallback 链可断言 |
| AL5 | 用 **fake backend + 计数队列** | 单写者串行、溢出策略、装配顺序可断言 |

### 7.2 集成验收

| 层级 | 内容 |
|---|---|
| **契约集成** | 在真实 Hermes 中激活；`prefetch` / `sync_turn` / `on_session_end` 全链路跑通 |
| **端到端** | 一段真实对话 → 记忆落库 → 下一会话召回命中 → 巩固提升可见 |
| **故障集成** | 断开 LLM / 断网 / 杀进程 → 验证 §6 降级矩阵逐条生效 |
| **合规集成** | CI 架构测试（R1–R6、R8–R10）+ 依赖扫描（R7）全绿 |
| **资产集成** | 导出档案后，**在无器灵的环境**用文本编辑器即可读懂全部记忆（INV-13 验证） |

**量化质量门槛**（评审 Q4 已定；benchmark 数字多来自厂商自报，须自测复现）：

| 指标 | 门槛 | **兑现里程碑** | 参照 |
|---|---|---|---|
| **LoCoMo** | **≥ 70** | M2（巩固/召回全量就位后首次自测） | 业界公开方案区间约 24–83（出处见 [RES-001](./03-记忆质量调研.md)）；≥70 取"优于多数公开方案"的位置 |
| **LongMemEval** | **≥ 75** | M2 → M4 复测 | Mem0 自报 94.4 为方向性目标 |
| `prefetch` 召回延迟 | p95 ≤ 300ms | M1（召回路径打通即测） | 与超时护栏一致 |
| `sync_turn` 延迟 | p99 < 5ms | M1（writer 队列就位即测） | INV-4 |
| 导出档案可读性 | 无器灵环境下人工可读 | M5（传承导出落地） | INV-13 |

> **门槛不是终局验收，而是里程碑出口条件**：M1/M2/M5 各自过不了对应门槛就不算完成该里程碑
> （与 §8 里程碑口径一致）。评测方法与固定语料见 [RES-001 §4](./03-记忆质量调研.md)。

# 器灵 / Artifact Spirit — 模型方案

> 设计记录（ADR-003，草案）
> 日期：2026-09-14
> 状态：**建议，待确认模型名单**
> 前提：用户拥有多模型 API Key（用量付费）、专属模型接口、TokenHub 多模型切换网关、多模型交叉验证能力。

---

## 1. 核心诉求

器灵不是「一个大模型包打天下」，而是「多类任务 × 多档模型」。五个诉求：

| # | 诉求 | 说明 |
|---|---|---|
| 1 | **分层** | 高频任务用小模型省成本，低频任务用大模型保质量，embedding 单独一类 |
| 2 | **结构化输出** | 提取/去重严格按 JSON schema 输出（`type`/`subject`/`predicate`/`object`/`scope`/`confidence`/`valid_from`/`valid_to`），记忆质量根基 |
| 3 | **协议统一** | 只实现 OpenAI 兼容协议，一套代码接所有 provider，不绑死任何一家 |
| 4 | **可交叉验证** | 巩固/核心记忆/去重等「错了就污染记忆」的任务，跑多模型交叉验证 |
| 5 | **成本可控** | 交叉验证只在关键任务用；高频走用量付费的小模型 |

---

## 2. 三档模型分层

| 档 | 模型 | 负责任务 | 频率 | 特征 |
|---|---|---|---|---|
| ① | Embedding 专用 | 向量化、语义检索 | 极高 | 维度稳定，与 LLM 不同类 |
| ② | 小模型（快而省） | 记忆提取、去重、分层摘要 | 高 | 用量付费、结构化输出强 |
| ③ | 大模型（强而贵）+ 交叉验证 | 巩固、反思、核心记忆更新 | 低（离线） | 多模型交叉验证降错 |

## 2.5 LLM / embedding 的具体应用场景

### embedding（纯向量化，不做理解）

| 场景 | 触发 | 输入 → 模型 → 输出 |
|---|---|---|
| 写入向量化 | 记忆入库时 | 记忆文本 → 向量 → 存 sqlite-vec |
| 检索向量化 | 对话前 `prefetch` | query → 向量 → KNN 相似度检索 |

**铁律**：写入与检索必须用**同一个 embedding 模型**（维度、语义空间一致），否则向量无法对齐。

### LLM（全部是「记忆加工」，无一例外）

| 场景 | 触发 | 输入 → LLM → 输出 | 频率 |
|---|---|---|---|
| 提取 extract | 每轮对话后 `sync_turn` | 对话 → 结构化事实 `{type/subject/predicate/object/scope/confidence}` | 最高频，小模型 |
| 去重 dedup | 新记忆入库前 | 新记忆 + 相似旧记忆 → ADD/UPDATE/MERGE/IGNORE | 中频，可交叉验证 |
| 摘要 summarize | 记忆沉淀时 | 全文 → L0 一句话摘要 | 中频，小模型 |
| 巩固 consolidate | 离线/后台定期 | 情景记忆 → 更高层语义 / 程序性记忆（情景记忆→语义记忆→程序性记忆） | 低频，大模型 + 交叉验证 |
| 核心记忆 soul | 极低频 | 本体相关表述 → 更新 identity/soul | 极低频，最强 + 交叉验证 |

> 核心：器灵调的 LLM 是「把对话里值得记住的东西抠出来、整理好、存进去」，不是「回应用户」。

## 2.6 与宿主（Hermes）的分工

**Hermes 的模型是「干活的」，器灵的模型是「记事的」，两套独立配置，互不干扰。**

| | 谁调 | 干什么 | 用什么模型 |
|---|---|---|---|
| Hermes 的 LLM | Hermes 自己 | 理解意图、调工具、生成回答 | 用户已在 Hermes 配置里选好 |
| 器灵的 LLM | 器灵 | 提取/去重/巩固/核心记忆 | 器灵三档配置（ADR-003） |
| 器灵的 embedding | 器灵 | 记忆向量化（写 + 检索） | 器灵独立配置 |

三点：

1. **并行不冲突**：器灵调用发生在 Hermes 钩子里（`prefetch` 前 / `sync_turn` 后），见缝插针
2. **成本两笔账**：Hermes token（回答）与器灵 token（记忆）分开；器灵那笔更小（小模型 + 增量 + 后台异步）
3. **可同源可不同源**：建议器灵独立配便宜模型（高频提取用 mini 档），不与 Hermes 前台大模型相互拖累

**OpenClaw**：另一 Agent 框架（Hermes 同类），与器灵无模型接口关系。器灵当前仅做 Hermes 的 MemoryProvider；若未来支持 OpenClaw 需另做宿主适配层，ModelProvider 可原样复用（它不依赖任何宿主）。

### embedding 与宿主的一致性（澄清）

embedding 无需与 Hermes 保持一致，向量也无需复用：

- **embedding 只「找」，LLM 才「懂」**：器灵 embedding 检索到记忆后，交付给 Hermes 的是记忆**文本**（非向量），故与 Hermes LLM 无对齐需求
- **缓存命中收益有限**：器灵 embedding 的文本（记忆事实 + query）与 Hermes 的文本（代码/文档）不同域，几乎不重叠；且记忆场景本身缓存少（记忆只写一次、query 几乎不重复）
- **向量应隔离**：用途不同（记忆相似度 vs 代码 RAG），物理隔离更安全（器灵 SQLite 独立迁移/重置）
- **选型优先级**：① 器灵内部一致性（写入=检索，硬约束）② 短文本语义质量 ③ 成本 ④ 与 Hermes 同源（纯加分项）
- **唯一值得「一致」的是 provider 层**：与 Hermes 共享 base_url/账号是省配置，不等于共享 embedding 模型

## 3. 任务 → 模型映射

```toml
[models]
embedding    = "kinfra-text-embedding-4b"   # 实测 2560 维，纯文本，支持 batch
extract      = "glm-5.3-flash"       # 高频小模型（快而省）
dedup        = "glm-5.3-flash"       # 可升级交叉验证
summarize    = "glm-5.3-flash"
consolidate  = "glm-5.3"             # 低频大模型 + 交叉验证
soul         = "kimi-k3"             # 核心记忆 + 交叉验证
```

- 小模型档：`glm-5.3-flash`（多模态，快而省）—— 结构化输出能力需实测，不稳则退 `glm-5.3`
- 大模型档：`glm-5.3` / `kimi-k3` / `minimax-m3` / `mimo-v2.5-pro` 均「深度思考」，作巩固/核心记忆 + 交叉验证池
- **embedding 定案**：`kinfra-text-embedding-4b`（**实测 2560 维**，batch 支持），备选 `kinfra-text-embedding-0.6b`（1024 维）；VL 系列（8b/2b）多模态，器灵纯文本用不上
- **建表**：`vec0(embedding float[2560])`，可选 binary quantization 压缩
- **铁律**：写入与检索同一 embedding 模型；换模型须 `aspirit reindex` 全库重嵌入（设计为内置工具）

## 3.5 配置模板（KEY / model 留空，运行时配置）

```toml
# $HERMES_HOME/artifact-spirit.toml

[provider]
# TokenHub（OpenAI 兼容网关）
base_url    = ""   # 如 https://tokenhub.tencentmaas.com/v1；留空 = 未配置，触发 fallback
api_key_env = "ARTIFACT_SPIRIT_API_KEY"   # key 从环境变量读，永不写进文件

[models]
embedding    = ""   # 待定（缺口）
extract      = ""
dedup        = ""
summarize    = ""
consolidate  = ""
soul         = ""

[cross_validation]
enabled = true
pool    = []   # 如 ["glm-5.3", "kimi-k3", "minimax-m3", "mimo-v2.5-pro"]
```

约定：**所有 KEY 经环境变量（前缀 `ARTIFACT_SPIRIT_`）注入，配置文件只放非敏感字段**（对齐 ADR-001 的 `save_config` 约定——密钥进 `.env`，非密钥进 JSON/TOML）。

## 3.6 fallback 机制

```
resolve_llm(task):
  1. [models] 有值 + provider 已配置 → 用 TokenHub（或指定 provider）
  2. 未配置 → 尝试宿主 Hermes 的 LLM 配置（读 hermes_home/config.yaml）
  3. 仍未 → 读通用环境变量（OPENAI_API_KEY / OPENAI_BASE_URL 等）
  4. 全无 → 报错，提示 aspirit setup 配置
```

- **LLM 可 fallback 到宿主**（借用 Hermes 的模型，属「兜底」非「推荐」——大模型做高频提取成本高）
- **embedding 不可 fallback 到 LLM**（LLM 非 embedding 模型）。embedding 未配置时，检索降级为 BM25/关键词兜底，或跳过向量检索并告警

### 3.7 provider 限流参数（已确认）

| 参数 | 值 | 对器灵的意义 |
|---|---|---|
| TPM | 1,000,000 tokens/分钟 | 极富余（embedding 短文本 + 提取约 7K token/次），无需特殊限流应对 |
| RPM | 300 请求/分钟 | 富余，但仍建议 **batch embedding** 合并多条，省请求数 + 省成本 |

结论：限流参数对器灵是「富余」的，正常批量策略即可；无需排队/退避等限流适配逻辑。

## 4. Provider 架构（OpenAI 兼容 + 可插拔）

```python
ModelProvider
 ├─ LLMProvider        → POST /chat/completions
 │    ├─ 直连 provider（OpenAI / 火山豆包 / 专属接口）
 │    └─ TokenHub provider（base_url 指网关，model 字段路由多模型）
 └─ EmbeddingProvider  → POST /embeddings
      └─ 同上，直连或经 TokenHub
```

- 器灵只实现一套 httpx 客户端，打 OpenAI 兼容协议
- 每个 provider = `base_url` + `api_key` + 可选模型名单
- TokenHub 本质是一个 `base_url` 指向网关的 provider，`model` 字段即路由键
- 切换网关/加模型/改 provider 只改配置，代码零改动

## 5. 交叉验证策略

只挂三个「高影响」任务，流程：

```
双模型独立作答
 ├─ 结果一致 → 通过
 └─ 结果不一致 → 第三模型仲裁，或标记「待人工复核」
```

- **启用**：dedup（去重决策）、consolidate（巩固提炼）、soul（核心记忆更新）
- **禁用**：extract / summarize（高频，成本失控）
- 交叉验证的结果与分歧记录进 audit，本身也是「可评审」的一部分

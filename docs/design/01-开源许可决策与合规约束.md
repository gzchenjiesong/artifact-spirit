# 器灵 / Artifact Spirit — 开源许可决策与合规约束

> 决策记录（ADR-001）
> 日期：2026-09-14（2026-09-15 修订：规则改为**按许可类别**表述，移除已废弃组件的专项分析）
> 状态：**已定**
> 结论：**器灵以 MIT 发布；依赖准入只看"许可类别"——禁止引入任何传染性许可（AGPL / SSPL）或许可不明的第三方包。**

---

## 1. 结论摘要

| 问题 | 答案 |
|---|---|
| 器灵用什么协议？ | **MIT** |
| 依赖准入的判据？ | 只看**许可类别**：public domain / MIT / Apache-2.0 / BSD 可**直接 import**；**AGPL / SSPL / 许可不明**一律禁止 |
| 为什么这么严？ | 许可**不可逆**——混入传染性许可，项目整体被迫同协议，且几乎无法摘除（§4） |
| 怎么强制？ | 依赖扫描门禁（R7 / INV-10）：源码 import（AST）与 `pyproject.toml` 声明**双向扫描**，命中即 CI 失败 |
| 有例外通道吗？ | 只有一条：**进程边界隔离的独立服务**（HTTP / CLI 调用，不 import、不 vendor、不分发）。当前默认栈**不需要**它 |

## 3. 传染性许可的判定边界（通用规则）

### 3.1 两条关键条款（以 AGPL-3.0 为例）

| 条款 | 内容 | 意味 |
|---|---|---|
| **§5(c)** | 包含该协议代码的作品，整体必须以同一协议授权 | **进程内 `import` = 单一作品 = 传染** |
| **§13** | 修改后通过网络对外提供服务，须向远程用户提供对应源码 | "原样运行"不触发；"修改并对外提供"才触发 |

### 3.2 决定性的边界：「聚合（aggregate）」

通行解释：**两个程序通过 socket / pipe / 命令行 / REST 通信，属于 arm's length（保持距离）交互，不构成结合作品**，因此不传染。

以及一句必须记住的反向判词：

> **"A plugin loaded into your process is not an aggregate."**
> （载入到你进程内的插件，不算聚合。）

**这一句直接命中器灵的形态**——器灵本身就是宿主的"插件"，运行在宿主进程内。所以：

- 器灵**进程内 import** 一个 copyleft 组件 → 同一 Python 进程 → **不是聚合** → 器灵整体被迫同协议
- 器灵**只通过 HTTP / CLI 调用独立进程** → **是聚合** → 器灵可保持 MIT

### 3.3 判定表

| 集成方式 | 代码形态 | 是否聚合 | 器灵可用协议 |
|---|---|---|---|
| 进程内 import 第三方包（copyleft） | 同一进程 | ❌ 否 | 仅**与对方同协议** |
| 进程内 import"许可不明"的包 | 同一进程 | ❌ 否 | 同上（**按最严推定**） |
| 自写 HTTP 客户端 → 独立服务进程 | 进程间 | ✅ 是 | **MIT 可行** |
| vendor / 复制源码进仓库 | 源码复制 | ❌ 否 | 仅与对方同协议 |
| 把对方二进制打进发行包 | 分发本体 | — | 须按对方协议履行 |

## 4. 为什么"反正全开源"仍要守这条线

常见直觉："我不商业化、本来就全开源，那依赖 copyleft 对我没区别，风险是下游的事。" 这个直觉对了一半，漏掉三件事：

1. **协议是不可逆的单程票。** `import` 了 copyleft 组件，项目就只能同协议——未来想改回 MIT / Apache 都做不到（代码已"长"进项目，摘除几乎等于重写）。**MIT → AGPL 可逆，AGPL → MIT 不可逆。** 作者心态与项目走向会变，锁定协议等于替未来的自己放弃选择权。
2. **生态萎缩对作者也是直接损失。** 开源项目最稀缺的是贡献者与使用者。copyleft 会让部分企业开发者不敢用、不敢贡献（大厂政策一刀切），结果是 issue 少、PR 少、采用率低。
3. **本项目生活在 MIT 生态里。** 宿主是 MIT；一个 copyleft 插件会在企业部署许可评估时被直接排除，等于主动把潜在用户挡在门外。

因此，**"默认栈只用可 import 的宽松许可依赖"成本几乎为零，却把未来的全部选项原样保留。**

## 5. 三条硬约束（MIT 方案的前提）

任何"外部服务型后端"（若未来引入）都必须同时满足以下三条，**不可妥协**，写入 `CONTRIBUTING.md` 与 CI：

### 约束一：禁止 import 对方的官方包 / SDK

```python
# ❌ 禁止 —— 进程内 import 触发 copyleft 传染
# from <copyleft_pkg> import Client

# ✅ 允许 —— 自写 HTTP 客户端，进程边界隔离
import httpx
resp = httpx.post(f"{endpoint}/api/v1/...", json={...})
```

### 约束二：禁止 vendoring

不把对方的任何源码、二进制、生成物复制进本仓库，仅通过运行时网络调用。

### 约束三：禁止分发对方本体

不 bundle、不重打包其服务端。只声明"需自行安装"，用户自行安装的服务由其自行履行许可义务。

**强制方式**：CI 依赖扫描（R7 / INV-10）——`pyproject.toml` **解析依赖名** + 源码 AST 扫 import，命中即失败。禁入清单**按许可类别维护**，具体包名只是该规则的已识别实例（见 `src/artifact_spirit/compliance/dep_scan.py`）。

## 6. 对架构的反向约束

| | 进程内嵌入 | 进程外 HTTP / CLI |
|---|---|---|
| 部署体验 | 零部署、单进程 | 需常驻服务 |
| 器灵协议 | **被迫同协议** | **可保持 MIT** ✅ |
| 多进程安全 | ❌ 单例、与宿主其他 provider 互斥 | ✅ |
| 结论 | 不采纳 | **本项目的形态** |

**连带约束**：`is_available()` 必须能在**不发起网络调用**的前提下判断可用性（宿主契约硬性要求）。因此可用性预检只能读配置与端口状态，不做探活。

> 器灵 MVP 的默认后端是进程内的 `SQLiteBackend`（依赖全为 public domain / MIT / Apache-2.0）。上述约束是为**未来任何外部后端**预留的准入线，不是当前依赖。

## 7. 备选方案对比

| 方案 | 器灵协议 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **A. MIT + 宽松许可依赖**（采纳） | MIT | 采用门槛最低；与宿主生态一致；企业可放心引入 | 须守三条约束；重型能力需自研 | 追求传播与生态 |
| **B. 全程 copyleft** | copyleft | 零许可争议；防闭源分叉 | 部分企业内政禁用，影响采用；**不可逆** | 明确要反闭源分叉 |
| **C. 分层许可** | MIT 核心 + copyleft 可选适配器 | 灵活，可支持外部服务后端 | 双包拆分、打包与文档复杂度上升 | 未来要接外部服务 |
| **D. MIT + 进程内嵌入 copyleft 库** | — | — | **许可上不成立** | ❌ 排除 |

## 8. 用户侧义务提醒（写入 README）

1. 器灵自身是 MIT，可自由使用、修改、分发。
2. 若用户自行安装任何 AGPL / SSPL 服务并与器灵通信，该程序的许可义务由用户自行承担。
3. **运行未经修改的 AGPL 服务不触发 §13**——这是最常见的误读，可放心使用。
4. 文档中提及第三方产品属描述性使用，不得暗示官方背书或合作关系。

---

## 9. 最终建议

**采纳方案 A：器灵以 MIT 发布，默认依赖全部为 public domain / MIT / Apache-2.0 / BSD。**

理由按权重排序：

1. **协议不可逆，而宽松许可方案成本几乎为零**（§4）
2. **架构本就该如此**：进程内单文件后端在多进程安全与部署体验上同时占优，合规理由只是让它从"更优"变成"必须"
3. **生态效益**：器灵是插件，MIT 能最大化采用面；宿主生态本身是 MIT，协议一致
4. **可强制**：三条约束由 CI 依赖扫描兜底，不依赖人的记性

若未来决定引入进程内嵌入的 copyleft 组件，**必须在提供该功能的同一提交中把仓库整体转为对应协议**，或走方案 C 的双包结构。不得两者兼得。

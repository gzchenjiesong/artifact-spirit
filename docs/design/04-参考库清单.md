## 2. A 类：宿主契约

### Hermes Agent（MIT · Nous Research）

- **参考什么**：`MemoryProvider` 抽象基类契约、`plugin.yaml`、`register(ctx)` 入口、entry-point 分发机制

> **⚠️ 契约清单于 2026-09-14 对上游源码逐条核对过，本条目原先的钩子名有误。**
>
> 核对方式与结果见 `docs/design/encoding/实现记录.md` §7，可复跑的脚本是
> `scripts/realtest/contract_diff.py`（`--fetch` 会重新拉取上游再比对）。
>
> **修正**：原文写的 `on_session_start` **在宿主里不存在**。真实的逐轮钩子叫
> `on_turn_start(turn_number, message, **kwargs)`。依赖一个不存在的钩子不会报错——
> 宿主 `_each_provider` 把 AttributeError 吞成一条日志，于是"每轮登记会话"这件事
> 从来没有发生过，而测试（只调用自己实现过的方法）永远发现不了。
>
> 宿主的完整方法集（`agent/memory_provider.py`，已核对）：
>
> | 类别 | 方法 |
> |---|---|
> | 抽象必需 | `name` / `is_available` / `initialize(session_id, **kwargs)` / `get_tool_schemas` |
> | 工具 | `handle_tool_call(tool_name, args, **kwargs) -> **str**`（返回 JSON 字符串，不是 dict） |
> | 召回 | `system_prompt_block()` / `prefetch(query, *, session_id)` / `queue_prefetch(...)` / `recall_status()` |
> | 写入 | `sync_turn(user_content, assistant_content, *, session_id, messages, turn_author)` |
> | 钩子 | `on_turn_start` / `on_session_end(messages)` / `on_session_switch(new_session_id, *, parent_session_id, reset, rewound)` / `on_pre_compress(messages)` / `on_delegation(task, result, *, child_session_id)` / `on_memory_write(action, target, content, metadata)` |
> | 配置 | `get_config_schema() -> **list[dict]**`（返回 dict 会让面板一个字段都不显示） / `save_config(values, hermes_home) -> None` |
> | 其它 | `unavailable_reason()` / `identity_signature()` / `backup_paths()` / `shutdown()` |
>
> **另外两条容易写错的契约**（都已修正）：
> 1. `handle_tool_call` 要返回 **JSON 字符串**；宿主失败时也用 `tool_error(...)` 即
>    `{"error": ...}` 的串。返回 dict 不报错，只是模型读到的工具结果变成 Python repr。
> 2. 后台任务（writer / maintenance / 超时护栏线程）必须走宿主的
>    `spawn_context_thread`——它把线程绑到**调用方的 contextvars** 上。用空上下文起的
>    worker 会静默写到默认 profile 的库里去。宿主文档原文：
>    *"Every memory-provider background job (prefetch, sync, writer loops) must go through this"*。
- **为什么参考**：器灵的宿主，接口契约必须精确遵守；`sync_turn` 须守护线程、存储须基于 `hermes_home`、单激活限制等硬约束
- **关键先例**：其 memory provider 机制（单激活约束、后台任务必须经 `spawn_context_thread`、存储必须基于 `hermes_home`）是器灵必须精确遵守的契约先例

## 3. B 类：质量对标（标尺）

**标尺不是某个产品，而是公开 benchmark 的数字**（数字与出处见 [RES-001 记忆质量调研](./03-记忆质量调研.md)）：

| 标尺 | 公开数字 | 器灵门槛 |
|---|---|---|
| **LoCoMo** | 公开方案约 24–83；厂商自报最优 80–83 | **≥ 70**（优于多数公开方案） |
| **LongMemEval** | 自报最优 94.4 | **≥ 75**（方向性追赶） |

- **参考什么**：被公开数据验证过的**范式共识**——能力栈分层（存储 / 检索 / 编排）、分级摘要（印象 → 概览 → 细节）、变更审计（diff 式留痕）、按类型分流的多类记忆提取、完整检索链路（意图分析 + 目录递归 + rerank）
- **为什么参考**：这些是业界已投入大量调优的范式，器灵**借范式不借依赖**（详见 [ADR-002 §4.1](./02-底层存储选型.md)）
- **复用方式**：**只作标尺与范式参照**。不 import、不 vendor、不打包（合规判定见 [ADR-001](./01-开源许可决策与合规约束.md)）

## 4. C 类：直接复用（依赖）

| 库 | 协议 | 参考什么 | 为什么 |
|---|---|---|---|
| **SQLite** | public domain | 关系存储、单文件、事务 | 真相源底座（`memories`/`audit`/`edges` 表），协议最宽松 |
| **sqlite-vec** | MIT/Apache-2.0 | `vec0` 虚拟表、KNN 检索、binary quantization（约 32x 压缩）、Matryoshka 截断 | 唯一直接复用的向量检索组件；零依赖、跨平台；几十万向量内暴力扫描即够用 |
| **httpx** | BSD-3-Clause | HTTP 客户端 | **LLM / embedding 服务调用**（记忆提取 / 摘要 / 去重 / 向量化的必需） |

## 5. D 类：借鉴设计（不依赖）

### Mem0（Apache-2.0 · open-core，YC S24）

- **参考什么**：ADD-only 单遍提取、结构化记忆 schema（`type`/`subject`/`predicate`/`object`/`scope`/`confidence`/`valid_from`/`valid_to`）、六态更新（ADD / UPDATE / INVALIDATE / MERGE / IGNORE / FORGET）、多信号检索（语义 + BM25 + 实体）、时间感知推理
- **为什么参考**：提取质量的最优参考（LoCoMo 92.5、LongMemEval 94.4，单遍提取 p50 约 1s / 约 7K token）
- **注意**：定位与器灵重叠（竞品），且 open-core + VC 支持有 relicense 风险 → **抄提取范式，不依赖**

### Graphiti / Zep（Apache-2.0 · 约 26.9k stars）

- **参考什么**：四层模型（Episode → Entity → Fact/Edge → Custom Ontology）、双时态（`valid_from`/`valid_to`）、混合检索（语义 + BM25 + 图遍历）、LLM 实体抽取、自动失效矛盾事实
- **为什么参考**：时序知识图谱的成熟范式，几乎就是器灵「情景记忆 + 语义记忆 + 扩散激活」的现成实现
- **注意**：图数据库后端均有坑（Neo4j GPL-3.0 / FalkorDB AGPL / Kuzu 已停维护）→ **抄数据模型，SQLite 自建轻量时序图（nodes/edges/facts 三表）**

### Letta / MemGPT（Apache-2.0 · UC Berkeley）

- **参考什么**：分层内存模型（core / recall / archival）、sleep-time 离线整合、自主记忆管理
- **为什么参考**：巩固的离线调度范式——把「记忆整理」从在线热路径搬到离线冷路径
- **复用方式**：借鉴「元认知」巩固引擎的调度时机

### LangMem（MIT · LangChain 生态）

- **参考什么**：semantic / procedural 记忆分类、background consolidation（后台巩固不阻塞主循环）、自更新指令层
- **为什么参考**：术语与器灵五类记忆最接近（semantic ↔ 语义记忆、procedural ↔ 程序性记忆），后台巩固范式
- **注意**：绑定 LangGraph，独立复用价值有限 → 抄分类 schema 与后台调度

### 斯坦福 Generative Agents（论文，非库）

- **参考什么**：`score = relevance + recency + importance` 三因子打分
- **为什么参考**：检索打分的业界金标准，是器灵「多因子融合召回」的源头
- **关键对应**：器灵公式 `α·语义 + β·活性 + γ·扩散 + δ·时间 + ε·核心记忆一致性` = 三因子的借鉴脑科学扩展版

### A-MEM（NeurIPS 2025）

- **参考什么**：Zettelkasten 自组织互联笔记、记忆进化（新记忆触发旧笔记的上下文/关键词/标签更新）
- **为什么参考**：关联记忆的自组织演化，器灵「扩散激活」的关联结构可借鉴
- **复用方式**：借鉴「语义记忆」关联网络的自组织更新

### 信息检索与知识组织经典（论文与范式，非库）

- **参考什么**：倒排索引 + BM25（Manning et al. 2008；Robertson & Zaragoza 2009）、排名融合 RRF（Cormack et al. 2009）、信息觅食与**信息气味**（Pirolli & Card 1999）、两阶段检索 rerank（Nogueira & Cho 2019）、递归摘要树（RAPTOR 2024）、知识组织的"目录 / 藏书分离"与分面分类（Ranganathan 1933；FRBR 1998）、个人知识管理（Zettelkasten；PIM）
- **为什么参考**：这是**知识型记忆**（外部资料积累）的直接来源——见 [DES-RES-004](./11-知识型记忆研究与机制增补.md)。其中 BM25 已采纳（`keyword_search`）、**RRF 是 M5 融合的可选备选**（比分数量纲归一化更省心）、rerank 已主动放弃并用"目录卡粗筛"补偿
- **注意**：这些是**论文与范式**，不引入任何代码依赖

## 7. F 类：评估后排除

| 对象 | 协议 | 排除原因 |
|---|---|---|
| Kuzu（Kùzu） | MIT | 2025-10 已归档停维护（Apple 收购 Kùzu Inc.），仅社区 fork |
| Neo4j 社区版 | GPL-3.0 | copyleft 服务依赖，需 HTTP 隔离 |
| FalkorDB | AGPL-3.0 | 回到 AGPL |
| Cognee | Apache-2.0 | 定位「组织级知识库」，与器灵「个人记忆编排」错位 |
| Supermemory | 闭源 SaaS | 自托管需企业协议 |
| MemClaw | 商业 | 定位「多 agent 集群治理」，非单用户记忆 |
| Mem0 图记忆 / Dream | 付费层 | open-core，高级能力在 Pro（$249/月） |

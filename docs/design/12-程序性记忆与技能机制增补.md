# 器灵 / Artifact Spirit — 程序性记忆与技能机制增补

> 文档编号：**DES-RES-005**
> 日期：2026-09-16
> 触发：**五类记忆里唯一"直接决定能力"的那一类，目前是空壳**——`procedural` 层已建表，但 `candidates()` 恒为空（C11 明令 MVP 不实现固化）。而助手的能力恰恰来自这类记忆：运动员的肌肉记忆、教师与工程师积累的做事流程、公司沉淀的 SOP、以及"这种情况上次怎么处理的"案例参考。
> 结论摘要：**归属不必争（`layer="procedural"` + `type="skill"` 早已存在），要争的是边界——器灵不做 skill 运行时、不复制技能正文、不自动改写技能。** 器灵管技能的四件事：**从哪来（导入 / 归纳）、什么时候用（触发条件）、用得怎么样（有效率）、怎么改进（候选 + 人审）**。它的索引键不是"主题"而是"**场合**"，它的生命周期不是"衰减"而是"**失效**"，它与宿主 skill 体系是"载体与记忆"的分工，不是两套竞争标准。

### 0.3 表述纪律

沿用 [TERM-000 §10](./06-术语与命名规范.md)：只引用**可检验的结论与量**，标注证据强度（**A** 多项独立验证 / **B** 单项经典或领域共识 / **C** 假说性），每条设计决策必须配 **Agent 侧判据 + 放弃条件**。

**术语纪律**：本文出现的 `skill` / `SOP` / `workflow` / 工具 / CLI / MCP 等词，**一律遵循 [TERM-000 §11](./06-术语与命名规范.md)**（三个域 + 中英对照 + 代码映射 + 禁用表）。要点速记：**技能（Skill）= 宿主的能力单元（`SKILL.md`）**；**技能条目（Skill Entry）= 器灵的 `type="skill"` 记忆表示**；**SOP = 技能条目的"编排形态"，不新增类型**；**`procedural` 是层名，`skill` 是类型名**；**`workflow` 仅用于引用 AWM 等研究原词，器灵无此实体**。

本文的引用主力是**技能习得的认知科学**（不是脑区定位）、**人类组织的流程与案例传统**（SOP / 检查单 / 案例推理 / 过程挖掘）、以及 **Agent 学界的 workflow 与技能归纳研究**（`workflow` 为英文学界原词，见 [TERM-000 §11.3(c)](./06-术语与命名规范.md)）。三者的共同点是：它们讨论的都是"**经验如何变成可复用的做事方式**"，比脑科学更贴题。

> **一条贯穿全文的差异**：人类的程序性记忆是**隐性的**（说不出来，只能做出来）；Agent 的技能是**显式的文本或代码**（可读、可审、可改）。这个差异不是小事——它意味着器灵**不能**照搬"做着做着就会了"，而必须**把技能变成可审的对象**（§2.1-7、§3 S7）。

## 1. 问题界定

### 1.1 现状：归属早已定，机制全空

| 事实 | 出处 |
|---|---|
| 术语表已定义：**程序性记忆（灵髓）· 永久 · 技能、可复用轨迹** | [TERM-000 §4/§5](./06-术语与命名规范.md) |
| `layer="procedural"` 与 `type="skill"` **已存在**（`memories.layer` / `memories.type`） | [AL3 存储层](./layers/AL3-存储层详细设计.md) `schema.sql` |
| 层级实现是**刻意留空的占位**：`candidates()` 恒返回空，不产出写意图 | `core/layers/procedural.py` |
| **C11**：程序性记忆 MVP **只建表**，不实现固化逻辑 | [LLD-AL2 §6 C11](./layers/AL2-核心层详细设计.md) |
| 语义 → 程序的固化**规则已定**，只是没实现：某模式成功复用 ≥ K 次 → 固化为 skill / trajectory | [LLD-AL2 §5 M2](./layers/AL2-核心层详细设计.md) |
| 优化任务**永不触碰** procedural 层（"技能误删代价不可接受"） | `core/consolidation.py` `NON_OPTIMIZABLE_LAYERS` |
| `skill` 不在可提升类型里（`PROMOTABLE_TYPES` 只含 fact/preference/entity） | 同上 |
| **"自更新指令层"已被裁决放弃**：与 Hermes skill 体系重叠 | [DES-REV-001 §3.4](./07-设计评审.md) |

**结论：不需要新增层、不需要新增类型、不需要新增表。** 本文要做的是把 C11 之后那一段补上——**技能从哪来、何时用、用得怎么样、怎么改进**。

### 1.2 三类内容要分开对待

用户口中的"程序性、功能性记忆"其实是三样东西，混在一起就没法设计：

| 类型 | 是什么 | 用户原话对应 | 归到哪 |
|---|---|---|---|
| **技能条目**（Skill Entry；含 **SOP** 编排形态） | 一套**可复用的做事步骤**：做什么、按什么顺序、有哪些要点与理由。**原子技能** = 单项能力；**SOP** = 多项技能 / 步骤按固定顺序的**编排**（[TERM-000 §11.4-③](./06-术语与命名规范.md)） | "教师 / 工程师积累的大量经验形成的做事流程"、"公司沉淀的 SOP" | `layer="procedural"` + `type="skill"` |
| **轨迹（trajectory）** | **一次具体执行**的完整过程（含工具调用序列、耗时、成败） | "这些流程在执行过程中也会不断积累各种改进细节" | `layer="episodic"` + `type="event"`，用 `relations` 挂到技能条目上 |
| **案例（case）** | "**这种情况上次是怎么处理的**"——症状 → 诊断 → 处置 → 结果 | "各种特殊情况如何处理的 case 案例参考" | `layer="procedural"`（知识性案例）或 `episodic`（经历过的事件），按内容分 |

> **为什么案例要单列**：SOP 管"常规怎么做"，案例管"**例外怎么办**"。人类组织的经验里，真正贵的是后者——它也是 [DES-RES-004 §2.1](./11-知识型记忆研究与机制增补.md) 里"分面分类"要表达的"适用范围"在技能侧的对应物。

### 1.3 与知识型记忆的分野：**索引键不同**

两者都是"外部或积累的、不常驻的、按需取用的记忆"，看起来可以合并，但它们的**检索入口完全不同**：

| | 知识型记忆（DES-RES-004） | 程序性记忆（本文） |
|---|---|---|
| 回答的问题 | "**关于 X 我知道什么**" | "**面对这种情况，我该怎么做**" |
| 检索入口 | **主题**（在讲什么） | **场合**（什么时候用） |
| 目录卡（L0）写什么 | 这条**讲什么** | 这条**何时用**、**别在什么情况下用** |
| 失效方式 | **过时**（版本 / 时效） | **失效**（版本 + **成功率** + 环境依赖） |
| 注入形态 | 片段 + 出处 | **步骤骨架 + 已知坑** |
| 共同点 | 都零常驻、都不参与时间衰减、都共享同一预算池、都走 L0/L1/L2 与 `spirit_recall` | 同 |

> 一句话：**知识是"我读到过"，技能是"我会做"。** 两者共用一整套基础设施，只是换了索引键与生命周期信号（§3 S3 / S6）。

### 1.4 边界：器灵**不是** skill 系统

这是本文最重要的一节。宿主（Hermes Agent）**本身就有** skill 体系，而且宿主已允许记忆 provider 注册技能——插件加载器的签名是 `load_memory_provider("artifact-spirit", register_skills=False)`，**器灵主动关掉了这条路**（`scripts/deploy/host_integration.py`）。这个选择是对的，理由如下：

| 职责 | 归谁 | 器灵的态度 |
|---|---|---|
| 技能的**可执行载体**（`SKILL.md` 目录、`scripts/`、工具定义、CLI） | **宿主** | 不复制正文、不另立格式 |
| 技能的**发现、加载、分发、版本安装** | **宿主** | 不注册 skill（维持 `register_skills=False`） |
| 工具与外部系统的接入（MCP / CLI） | **宿主** | 不做 MCP 服务端、不做工具网关 |
| **这个场合该不该用哪个技能** | **器灵** | 触发条件匹配 + 历史有效率 |
| **上次这么做失败了 / 有什么坑** | **器灵** | 案例与轨迹证据 |
| **这个 SOP 该怎么改** | **器灵产出候选，宿主或人确认** | 绝不自动改写技能（§3 S7 红线） |

> **一句话分工：宿主管"技能是什么"，器灵管"技能何时用、用得如何、哪里踩过坑"。**

**明确不做**（与 [README「明确不做」](../../README.md) 和 [DES-000 §1.2 非目标](./00-方案设计.md) 一致）：

- 不做 Agent / harness，不做 skill 运行时、不做 skill 市场与分发
- 不复制技能正文（技能的可执行真相在宿主的文件系统里）
- 不做 MCP 服务端、不做工具网关、不做浏览器 / RPA 执行器
- 不自动改写任何技能载体（`SKILL.md`、脚本、工具定义）
- 不引入 BPM 引擎 / 工作流引擎（与"零服务依赖"冲突）

## 2. 研究依据（四支）

引用格式同 DES-RES-003：**结论 + 强度 + 对设计的直接含义**。

### 2.1 技能是怎么形成的、怎么退化的（认知科学）

| # | 结论 | 强度 | 直接含义 |
|---|---|---|---|
| 1 | **三阶段模型**（Fitts & Posner 1967）：认知期（边想边做）→ 联结期（错误减少）→ **自动期**（不再占用注意力） | A | 技能不该"一键生成"，而应记录**当前处于哪个阶段**；只有进入自动期（连续成功）才值得免推理直接调用 |
| 2 | **ACT\* 的程序化（proceduralization）**（Anderson 1982）：先以**陈述性**形式编码（可读的规则），再"编译"成固定序列 | A | **技能的两层结构有理论根**：L1 抽象脚本（陈述性、可审）+ L2 具体执行（编译产物）——与 §2.3-3 的 Mem<sup>p</sup> 实验一致 |
| 3 | **自动性与变异性**（Shiffrin & Schneider 1977）：映射**一致**时自动化，映射**变化**时始终保持受控加工 | A | **环境不稳时固化是负债**（网站改版、API 变更）→ "环境依赖"必须进技能的失效信号（§3 S6） |
| 4 | **练习幂律**（Newell & Rosenbloom 1981；Anderson ACT-R）：收益随练习次数递减 | A | 固化门槛应按**边际收益**而非单纯次数；不要无限精化一个已经够好的技能 |
| 5 | **组块化**（Graybiel 2008 习惯的 chunking；Miller 1956）：行为被压成"步骤块" | B | 技能的记忆单位是**步骤块**，不是单步 → 与工作记忆 4±1 组块（[AL2 §5 M6](./layers/AL2-核心层详细设计.md)）同源；不要拆到原子步 |
| 6 | **离线巩固**（Walker et al. 2002 睡眠依赖的运动技能巩固；Stickgold） | B | 技能的固化属于**离线维护窗口**（AL5 maintenance），与 M2"离线执行"一致，**不进热路径** |
| 7 | **陈述 / 非陈述记忆分离**（Squire 1992/2004）：程序性记忆**难以言语化**、不被意识直接通达 | A | ⚠️ **关键差异**：人类技能"说不出来"，Agent 技能**可读可写**。因此不能指望"自动涌现"，必须**显式产出候选 + 人审**（§3 S7）——否则会静默漂移 |
| 8 | **实例理论**（Logan 1988）：自动化来自**直接检索实例**，而非每次重新计算 | B | 支持**案例层（L2）**的存在意义：熟悉的场合直接取"上次怎么做的"，不必展开抽象规则 |
| 9 | **刻意练习**（Ericsson et al. 1993）：提升来自**反馈 + 针对薄弱点的修正**，而非重复 | A | 技能必须带**执行反馈闭环**（S7）；没有反馈的"固化"只是重复 |
| 10 | **技能迁移与干扰**：前摄 / 后摄干扰（经典条件性研究） | B | 技能版本要能**并存与取代**，不能原地覆盖 → `superseded_by` / `valid_to` 同样适用 |
| 11 | **不用则退 / 去自动化**（技能衰退研究） | B | ⚠️ **与 M3 的关系**：技能**不因未访问而失真**（与知识一致），故**豁免时间衰减**；但"生疏"确实是真现象 → 用**成功率与最近成功时间**表达，而不是降权到消失（§3 S6） |

**不可照搬（三条边界）**：

1. 人类技能依赖**身体与感知运动回路**；Agent 没有肌肉，"肌肉记忆"在器灵里的对应物只是"**工具调用序列的免推理执行**"。
2. 人类技能**不需要被写下来**；Agent 的技能**必须被写下来**——这使"记录了技能"本身就有价值，也让"改写技能"成为高风险动作。
3. 人类练习的时间尺度是**几周到几年**；Agent 的"练习"是**几十次任务**。所以"M2 成功复用 ≥ K 次"里的 K 必须**小得多**，且要能被真实数据修订。

### 2.2 人类组织怎么沉淀流程与例外（SOP / 检查单 / 案例法 / 过程挖掘）

| # | 结论 | 强度 | 直接含义 |
|---|---|---|---|
| 1 | **作业分解 + 要点 + 理由**（TWI「工作指导」1940s；Taylor 1911 科学管理）：有效的作业标准不是步骤清单，而是**每步的关键点与为什么** | B | **SOP 的最小单元 = 步骤 + 要点 + 理由**。只有步骤没有要点的 SOP 在异常时立刻失效——这正是用户说的"改进细节"该记在哪 |
| 2 | **检查单胜过手册**（Gawande 2009 *The Checklist Manifesto*；WHO 手术安全清单）：短清单显著降低失误，长文档几乎不被执行 | B | **注入的必须是骨架 + 易错点**，不是整篇 SOP（§3 S5）；"长"本身就是失败原因 |
| 3 | **案例推理四步 RRRR**（Schank 1982 *Dynamic Memory*；Aamodt & Plaza 1994）：**Retrieve → Reuse → Revise → Retain** | A | ④**Retain（修正后回存）是关键**：案例库不是归档，而是**"这次怎么改的"必须写回**——对应 S7 的反思与改进候选 |
| 4 | **结构化流程用引擎、例外情形用案例法**（BPM / case management 两派；S-BPM 与 Adaptive Case Management） | B | Agent 面对的是**非结构化**任务 → 以案例法为主，**不引入流程引擎**（与"零服务依赖"一致） |
| 5 | **过程挖掘揭示"声称的流程 ≠ 实际的流程"**（van der Aalst, *Process Mining* 2016）：真相在**事件日志**里 | A | 技能改进的证据应该来自**执行轨迹**，而不是人的回忆或文档；归纳时要**把偏差当信号**而非噪声 |
| 6 | **流程文档必然腐化**：CMMI 式形式化催生 Agile 反弹；SRE 的 runbook 逐步被 "playbook as code" 取代 | B | **SOP 必须与执行反馈绑定**，否则一年后就是死文档；"可执行 / 可验证"是防腐剂（§2.3-2 SkillWeaver 同结论） |

> **这两节的合并结论**：人类几百年的组织经验指向同一件事——**流程的价值在"被执行的次数"与"被修正的记录"上**，而不在流程文档本身的完备性上。器灵如果要存 SOP，就必须一并存**执行与修正**，否则只是又一个知识库。

### 2.3 Agent 学界与业界：经验如何变成可复用技能

#### 2.3.1 从轨迹归纳流程（学术侧，最直接对口）

| # | 研究 | 做法 | 结果（**论文自报**） | 对器灵的含义 |
|---|---|---|---|---|
| 1 | **Agent Workflow Memory**（AWM，Wang et al., ICML 2025，arXiv:2409.07429） | 从**历史轨迹**归纳可复用 workflow，支持**离线归纳**（预先从训练轨迹抽取，注入首轮）与**在线归纳**（测试时边做边归纳） | Mind2Web 相对成功率 **+24.6%**、WebArena **+51.1%** | 「**从经验归纳流程**」这件事有正收益且已可落地；**但它产出的是自然语言 workflow——回答"该做什么"，不能直接执行** |
| 2 | **SkillWeaver**（Zheng et al. 2025，arXiv:2504.07079） | **propose → practice（多例打磨）→ distill 成可执行 API**，技能库跨模型复用 | 相对成功率 **+31.8%**（WebArena）/ **+39.8%**（真实网站）；跨模型迁移最多 **+54.3%** | 技能的**正确形态是"可验证 + 可组合的可执行物"**；且 **practice 只能筛掉不稳定技能，无法修正错误技能**（→ 修正必须靠人/外部反馈，§3 S7） |
| 3 | **Mem<sup>p</sup>：Exploring Agent Procedural Memory**（ACL 2026 Findings，arXiv:2508.06433） | 对比三种程序表示：**Trajectory（原始轨迹）/ Script（抽象脚本）/ Proceduralization（轨迹 + 高层脚本）**；并系统比较**构建 / 更新 / 检索**三阶段 | **Proceduralization 全模型全数据集最优**：ALFWorld 42.14 → **77.86**（相对 **+35.7%**），步数 23.76 → **15.01** | ⭐ **本文最重要的实验支撑**：技能条目应当是"**抽象步骤 + 具体案例**"双层，而不是纯 SOP 或纯轨迹（= 器灵的 L1 骨架 + L2 案例） |
| 4 | 同上（检索消融） | 对比"用什么当检索 key"：原始 query / 任务关键词 / 事实均值等 | **瓶颈在 key 构造而非相似度算子**（最优 key 76.02 vs 原始 query 73.38） | ⭐ **技能匹配要按"场合 key"检索**，不能把 query 直接丢进向量（§3 S3 的直接依据） |
| 5 | 同上（更新策略） | 对比：直接追加 / 只保留成功轨迹 / **反思式修正（Adjustment）** | **反思式修正最好**（再 **+0.7** 分、少 **14** 步） | ⭐ 失败后的**原地修正**是最有效的技能更新方式 → 这正是 S7 的养护闭环 |
| 6 | **Voyager**（Wang et al. 2023） | 技能以**可执行代码 + 描述**入库，用**自验证**筛选 | 开放世界中持续能力增长 | 技能要带**成功判据**，否则无法自动筛选；"描述"就是技能目录卡 |
| 7 | **ExpeL**（Zhao et al. 2024）/ **Reflexion**（Shinn et al. 2023） | 跨任务的**经验与反思**直接进上下文，不做固化 | 明显提升成功率（低成本） | **降级方案**：不做固化也能受益；若 S7 长期无产出，可退回"每次现推 + 案例参考"（§6.3） |

> **学术侧的三条硬结论**：① 流程归纳有效，但要**可验证**才可靠；② 技能的**两层结构（抽象 + 实例）**优于单层；③ 改进的杠杆在"**反思式修正**"，不在"多存轨迹"。

#### 2.3.2 标准侧：技能已收敛出与器灵**同构**的三级披露

| 事实 | 出处 | 对器灵的含义 |
|---|---|---|
| 一个 skill = **一个目录**：`SKILL.md` + 可选 `scripts/`（可执行代码）/ `references/`（文档）/ `assets/`（模板与资源） | Agent Skills 规范（[agentskills.io/specification](https://agentskills.io/specification)，2025–2026 成为跨工具事实标准） | 技能的自然单元是**目录**，与"技能条目 + 附件"一致；器灵**引用**它，不复制它 |
| frontmatter 必填 **`name`**（≤64 字符、小写连字符、**须与目录同名**）与 **`description`**（≤1024 字符，必须写清"**做什么**" + "**何时用**"） | 同上 | ⭐ **`description` 必须写"何时用"——与本文 S3"技能索引键是场合"独立吻合** |
| **三级渐进披露**：① 元数据（约 **100 token**，启动时全量加载）→ ② 指令正文（建议 **< 5000 token**，激活时加载）→ ③ 资源文件（按需读取） | 同上 | ⭐ **与器灵 L0/L1/L2 同构**。业界已收敛到同一形状 → 器灵**不发明新格式**，价值在**记忆与治理**，不在格式 |
| 建议 `SKILL.md` **< 500 行**、引用**只允许一层深** | 同上 | 与"禁止注入整篇"一致（§3 S5） |
| **MCP** 三原语：`resources`（资源）/ `prompts`（模板）/ `tools`（可调用工具）；2026-07-28 修订版规范 | [modelcontextprotocol.io](https://modelcontextprotocol.io/specification) | 工具与资源的**提供**是宿主职责；器灵若对外暴露能力，走**工具**（`spirit_*`），**不实现 MCP 服务端** |

> **战略结论**：**标准已经把"技能该长什么样"占满了，器灵再去定义一套技能格式就是重复建设。** 器灵要做的是标准**没管**的那半张桌子——**这个技能什么时候该用、上次用了成不成、哪里要改**。

#### 2.3.3 企业侧与中文实践

| 观察 | 对器灵的含义 |
|---|---|
| **「从 Skill 到 SOP」**：先有原子技能（可调用的能力），再把技能**编排**成 SOP 流程 —— 这是当前企业落地的典型路线 | 器灵的两类内容正好对应这条路线：**技能条目 = 原子能力**、**SOP = 编排**；没有"编排"就不叫 SOP |
| 企业强调"把**经验**封装成智能体**可调用的能力**"，而不是把文档塞进知识库 | 器灵的价值主张与此一致：**可被检索到 = 可被调用**；文档式知识留在知识通道，能力式经验进技能通道 |
| 记忆研究综述（2026）把记忆演化描述为 **Storage → Reflection → Experience** 三段，并指出"反思"是中间必经态 | 支持 S7：**先反思出候选，再固化**；跳过反思直接固化，等于把噪声写进技能 |

### 2.4 业界当前的方向（五条，以及它们留下的空位）

| 方向 | 谁在推 | 成熟度 | **留下的空位（器灵的机会）** |
|---|---|---|---|
| ① **技能载体标准化**（`SKILL.md` + 三级披露 + MCP 工具） | 各家 harness / 工具链 | 已成事实标准 | 标准**不管"何时用"的历史与效果** |
| ② **从轨迹归纳流程**（AWM / Mem<sup>p</sup> / SkillWeaver） | 学术 | 论文有效，工程刚起步 | **归纳出的东西无人审、无版本、无治理**；AWM 产物不可执行 |
| ③ **技能可执行化 + 自验证**（Voyager / SkillWeaver） | 学术 + 部分产品 | 有效但受限 | **只能筛不稳定，修不了错**；技能库膨胀会互相干扰 |
| ④ **记忆走向"经验 + 反思"**（Storage → Reflection → Experience） | 学术 + 记忆产品 | 概念清晰、实现零散 | 反思产出的**没人接住**（不写回、不进审计） |
| ⑤ **企业 SOP 沉淀** | 企业实践 | 大量人工 | 文档与执行**两张皮**（过程挖掘早已证明） |

> **空位收敛为一句话**：业界的技能体系**做得很好的部分是"技能的样子与执行"，做得很差的部分是"技能的记忆与养护"**——而这个空位恰好就是器灵的定位。

### 2.5 研究 → 设计：一句话对应表

| 研究给的 | 落到哪 |

| 实践只能筛不稳定、修不了错（§2.3-2） | 自动改写技能**禁止**；修正必须人/外部反馈（S7 红线） |
| `description` 必须写"何时用"（§2.3-2 标准） | 技能的 L0 目录卡 = **触发条件**（S3） |

| 刻意练习靠反馈（§2.1-9） | 没有反馈就不固化（S7） |
| 过程挖掘：偏差是信号（§2.2-5） | 轨迹与 SOP 的**偏差**进案例库（S1/S7） |
| 案例推理 Retain（§2.2-3） | 案例库要**回存修正**，不只归档（S7） |
| 技能迁移与干扰（§2.1-10） | 版本**并存与取代**，不原地覆盖（S6） |

## 3. 机制设计：技能通道（Skill Channel）

> 一句话：**技能的样子归宿主，技能的记忆归器灵。**
> 下文 S1–S8 是八条设计决策，每条配"依据 + 落点 + 判据"。

### 3.1 S1 归属与三类内容：**不新增任何东西**

| 内容 | 存法（全部复用现有结构） |
|---|---|
| **技能条目**（Skill Entry） | `layer="procedural"` + `type="skill"`；`content` = 步骤骨架（含要点与理由），**SOP 编排亦写在此**；`abstract` = **触发条件**；`scope` = 适用范围；`entities` = 涉及的工具 / 系统（**注**：`type` 恒为 `skill`，**不新增 `sop` 类型**——[TERM-000 §11.8](./06-术语与命名规范.md)） |
| **轨迹（一次执行）** | `layer="episodic"` + `type="event"`（或 `intent`），用 `relations` 挂到技能条目；成败与耗时写在内容里 |
| **案例（例外情形）** | `layer="procedural"`（知识性案例）或 `episodic`（经历型案例），成对记录"**症状 → 诊断 → 处置 → 结果**" |
| **技能与案例的关联** | `relations`（复用白名单，见 §5.2 G-d） |

| 项 | 内容 |
|---|---|
| 依据 | `procedural` / `skill` 已存在；C11 只约束"固化逻辑"，不约束"记录与检索" |
| 落点 | **不改 schema、不新增层 / 类型 / 表** |
| 判据 | 技能条目能被 `spirit_recall(layers=["procedural"])` 检索到（**layer 过滤已支持，无需新增参数**——这一点与知识型记忆的缺口不同） |

### 3.2 S2 三层承载：**与 `SKILL.md` 三级披露同构**

| 器灵 | 对应 `SKILL.md` 结构 | 内容 | 体量 |
|---|---|---|---|
| **L0** | `description`（元数据） | **触发条件**（何时用 / 何时不要用）+ 代价与风险 | ≤ 24 token（沿用既有常量） |
| **L1** | `SKILL.md` 正文 | **步骤骨架 + 每步要点 + 理由 + 已知坑** | ≤ 500 行；注入时 ≤ 400–600 token |
| **L2** | `scripts/` / `references/` | 具体案例、轨迹片段、可执行脚本的**引用**（不是副本） | 按需 |

| 项 | 内容 |
|---|---|
| 依据 | §2.3-2（标准同构）+ §2.3-3（Proceduralization 最优）+ §2.2-1（要点与理由） |
| 落点 | 完全复用 `L0/L1/L2` 与 `spirit_expand`；**不新增编号、不改格式** |
| 判据 | 只看 L0 能判断"这个场合要不要展开"；展开到 L1 能照着做；有例外时能到 L2 找案例 |

### 3.3 S3 索引键是**场合**，不是主题（本文最独特的一条）

| 项 | 内容 |
|---|---|
| 依据 | §2.3-4（检索瓶颈在 key 构造）+ §2.3-2（`description` 必须写"何时用"）+ §2.1-3（环境变异敏感） |
| 触发条件写什么 | ① **任务类型**（"给项目加一个新数据源"）② **前置条件与工具**（"项目是 Python + SQLite"）③ **反例**（"**不要**用于生产库迁移"）④ **代价**（耗时 / 风险等级） |
| 检索 key 怎么构造 | 用 **`intent`（工作记忆意图槽，已存在）+ 任务关键词** 组合成查询，而不是把原始 query 直接丢进向量（§2.3-4 的消融结论） |
| 落点 | `abstract` 存触发条件（L0）；不新增字段。**降级方案**：查询由调用方构造（技能匹配先走关键词路），暂不动 M5 因子（§5.2 G-a） |
| 判据 | **场合误匹配率**：用了不该用的技能的比例；以及"该用没用"的漏匹配率 |

### 3.4 S4 唤醒：两条通路，**优先级高于知识**

| 通路 | 机制 | 何时触发 |
|---|---|---|
| ① **场合触发（自动）** | 任务开始 / 意图切换时，按 S3 的 key 匹配**至多 1–2 条**技能，只给 L0 + L1 骨架 | 意图槽变化、任务类型识别 |
| ② **显式检索（主动）** | `spirit_recall(layers=["procedural"])` + `spirit_expand(L0/L1/L2)` | 模型自己判断"这类任务我以前做过，查一下" |
| 共用 | 双路并行召回（`vector_search` + `keyword_search`）→ M5 六因子融合 | 与经历型 / 知识型记忆同一套 |

| 项 | 内容 |
|---|---|
| 依据 | §2.4-3 交互记忆（DES-RES-004）"知道有，才去取"；§2.2-2 检查单（一次命中） |
| 不做 | 不做"技能路由模型"、不做 rerank、不做意图分类器（沿用 [AL2 §5 M5](./layers/AL2-核心层详细设计.md) 的"放弃意图分析"裁决） |
| 判据 | 技能命中率；注入后任务成功率的变化（§6.2） |

### 3.5 S5 注入护栏：**只给骨架与坑**

| 护栏 | 取值 | 依据 |
|---|---|---|
| L0 目录卡 | ≤ 24 token/条 | 既有常量 |
| 自动注入条数 | ≤ **2** 条/轮（仅 L0 + L1 骨架） | 注意力预算（DES-RES-003 §2） |
| 技能注入预算 | ≤ 本轮记忆注入预算的 **1/3**；与知识型记忆**共享**该额度，**技能优先** | §2.1-5 组块 + 预算池观 |
| L1 注入长度 | ≤ 400–600 token；**禁止注入整篇 `SKILL.md`** | §2.2-2（检查单 vs 手册）、P3 分级抽象 |
| 危险步骤 | 含**删除 / 外发 / 付费 / 权限变更**的步骤，注入时必须带「**需确认**」标注，**不得自动执行** | 治理红线（§3.8 S8） |
| 常驻系统提示 | 技能**不进** `system_prompt_block` 常驻区 | 与知识型记忆同纪律（K5） |

> **与知识型记忆唯一的优先级差异**：预算不足时**先舍知识、后舍技能**——技能直接决定"做得对不对"，知识只决定"答得全不全"。

### 3.6 S6 生命周期：**不衰减，管"失效"**

| 项 | 内容 |
|---|---|
| 依据 | 术语表已定程序性记忆为**永久**；§2.1-11（不用则退是"生疏"不是"失真"）；§2.1-10（迁移与干扰） |
| 裁决 | **豁免 M3 时间衰减**（与知识型记忆一致）。`NON_OPTIMIZABLE_LAYERS` 已含 `procedural`，语义自洽 |
| 三条失效信号 | ① **版本**：被新版取代 → `superseded_by` / `valid_to` ② **有效率**：用了 N 次、失败 M 次 → 降权 ③ **环境依赖**：目标产品 / 依赖 / 界面变了（§2.1-3 变异映射）→ 标记"可能失效" |
| 有效率怎么存 | **派生量**：从 `audit` 与关系边离线重放统计（INV-12 派生态纪律），**不新增列**。需要新增关系类型时走 G-d 接口变更 |
| 判据 | **技能有效率**（成功 / 总使用）；**失效发现时延**（技能坏了多久被发现） |

### 3.7 S7 养护闭环：**器灵产出候选，人 / 宿主确认后写回**

> 这是本文与知识通道最大的不同：知识只要"记准"，技能必须"**练好**"。

```
执行技能 → 反馈（成功 / 失败 / 人工修正）
        → 反思（离线，生成"技能改进候选"：哪一步有问题、建议怎么改）
        → 人 / 宿主确认
        → 写回技能载体（SKILL.md / 脚本 / 流程）
        → 版本与有效率更新（S6 信号）
```

| 项 | 内容 |
|---|---|
| 依据 | §2.2-3 案例推理的 **Retain**；§2.2-5 过程挖掘（偏差是信号）；§2.3-5 反思式修正最有效；§2.1-9 刻意练习（反馈 + 针对性修正） |
| **红线** | 器灵**绝不自动改写技能正文**（`SKILL.md` / 脚本 / 工具定义）。三条理由：① 技能的**可执行真相在宿主文件系统**（INV-1 的类比：真相唯一，器灵只持有引用与证据）② [D-12](./00-方案设计.md) 的 A-MEM 纪律已定"**不改 `content`，只改 `abstract` 与边**"，技能正文更贵 ③ §2.1-7 的差异推论：Agent 技能可读可写，**更需要人审**，而不是更不需要 |
| 输出物 | **技能改进候选** = 一条待审记忆 + 一段建议 diff（进 `audit`、可导出、可审查） |
| 触发时机 | **离线维护窗口**（AL5 maintenance），与 M2 巩固同批；**不进热路径** |
| 退化路径 | 若长期无人采纳（改进采纳率 ≈ 0）→ **停掉反思，只保留"案例检索"**（§6.3），避免产生垃圾候选 |
| 判据 | **改进采纳率**（被采纳候选 / 生成候选）；采纳后技能有效率的变化 |

### 3.8 S8 治理：冲突、危险、缺口、不删

| 项 | 内容 | 依据 |
|---|---|---|
| **重名 / 冲突检测** | 与宿主已有 skill 同名、或两个技能步骤重叠度过高 → **提示合并，不覆盖、不静默新增** | §2.3-2 SkillWeaver 的失败模式：技能库膨胀会互相干扰（论文自报冲突率 2.3%） |
| **重复检测** | 精确去重复用 `content_hash`（D-21 / INV-14）；近重复是增量能力 | 同上 |
| **危险技能标记** | 步骤涉及删除 / 外发 / 付费 / 权限变更 → 注入时带「需确认」，且**不得自动执行** | 安全 |
| **缺口可见** | 遇到没做过的任务类型 → 显式说"我没有这类经验"，**不要硬编一个流程**（编造 SOP 比编造事实更危险） | §2.4-1 交互记忆 / 知晓感（与知识通道 K7 同一机制） |

## 6. Agent 侧判据（验收）

### 6.1 指标

| 指标 | 定义 | 目标 |
|---|---|---|
| **技能命中率** | 该用技能时，它出现在候选 / 被显式检索到 | ↑（主指标） |
| **场合误匹配率** | 用了**不该用**的技能的比例（S3 的直接检验） | ↓（比命中率更该盯） |
| **漏匹配率** | 该用却没用（有技能但没被想起） | ↓ |
| **技能有效率** | 成功次数 / 总使用次数（按技能、按版本） | ↑；连续失败触发"可能失效" |
| **注意力占用** | 技能注入 token / 该轮记忆注入总 token | **≤ 1/3**，且无技能时 ≈ 0 |
| **危险步骤拦截** | 含删除 / 外发 / 付费 / 权限变更的注入是否都带「需确认」 | **100%** |
| **改进采纳率** | 被采纳的改进候选 / 生成的候选 | ↑（若长期 ≈ 0 → 停掉反思，§6.3） |
| **重名 / 冲突数** | 与宿主 skill 或库内技能重名、重复未被提示的次数 | **0** |
| **失效发现时延** | 技能实际失效 → 被标记的时间差 | ↓ |

### 6.2 对照实验（三组，关键是第二组）

| 组 | 技能记忆的用法 |
|---|---|
| **A（基线）** | **无技能记忆**：每次任务从零推理流程 |
| **B（本设计）** | 技能条目 + **场合匹配**（触发条件 key）→ 注入 L0 + L1 骨架，例外时展开 L2 案例 |
| **C（对照）** | 技能条目 + **纯 query 向量匹配**（不构造场合 key） |

**必须同时看**：任务成功率（↑，主要看复杂 / 长流程任务）+ 注入 token（↓ 或持平）+ **步数**（Mem<sup>p</sup> 报告步数显著下降，是"自动化"的直接信号）。只看成功率不看 token，会漏判"因为多塞了内容才变好"。

> **B vs C 是本文最该做的一次小实验**：它检验的是 S3（场合 key）在器灵场景是否复现 Mem<sup>p</sup> 的结论。若 B ≈ C，说明场合 key 无增益 → S3 应当降级为"直接用查询"。

### 6.3 放弃条件

| 若…… | 则…… |
|---|---|
| B 不优于 A，且 token 也没降 | 技能通道不成立 → 退回"只存案例（L2），不存 SOP" |
| B ≈ C（场合 key 无增益） | S3 降级：不做触发条件索引，直接用语义 + 关键词检索 |
| 固化后成功率反而下降 | **过度固化 / 环境漂移** → 停固化，退回"每次现推 + 案例参考" |
| 改进候选采纳率长期 ≈ 0 | 反思产出无人接住 → **停掉反思**（S7 只保留"反馈记录"） |
| 与宿主 skill 的重名 / 冲突持续发生 | 停止导入外部 SOP，只保留"经验案例"，避免两套真相打架 |
| 注入 1/3 预算仍显著挤占任务表现 | 下调上限；或改为"仅在模型显式检索时注入" |
| AGENTS / harness 已原生提供"技能使用统计 + 改进建议" | 器灵**退出该子职责**（只保留记忆与审计），避免重复建设 |

## 7. 与业界做法的分野

| 能力 | 宿主 skill 体系 / 业界技能库 | 器灵（技能通道） |
|---|---|---|
| 技能的**载体** | 目录 + `SKILL.md` + `scripts/`（标准形态） | **不承载**：只存引用 + 触发条件 + 证据 |
| **渐进披露** | 三级（元数据 / 正文 / 资源） | **同样三级**（L0/L1/L2）→ **同构，不是竞争** |
| **归纳** | AWM（从轨迹归纳 workflow）/ SkillWeaver（propose-practice-distill） | **不自动固化**（M5 才做，且优先借用外部归纳器） |
| **检索** | 按名字 / 描述匹配，或由模型自行选择工具 | 按**场合**匹配（触发条件）+ **历史有效率** |
| **反馈** | 少见（SkillWeaver 用 practice 筛稳定性） | **有效率派生** + 改进候选（**不自动写回**） |
| **治理** | 通常没有（版本靠文件、失败靠日志） | **有**：审计 / 可审 / 可恢复 / 冲突检测 / 危险标记 / 不删 |
| **迁移** | 技能库跨模型迁移（SkillWeaver 报告 +54.3%） | 可导出（V3）→ `SKILL.md` 草稿，但**不承载执行** |
| **与其它记忆的关系** | 独立系统（与记忆各管一段，常无交集） | **同一套记忆体系的一员**：共享预算、调度、审计 |

> 一句话：**器灵不是 skill 系统，而是技能的记忆与养护层——技能的可执行真相永远在宿主手里。**

## 10. 一句话总结

> **程序性记忆的归属早就定了（`procedural` 层 + `skill` 类型），缺的是"技能从哪来、什么时候用、用得怎么样、怎么改进"这四件事。** 而业界恰好把前半段做透了（`SKILL.md` + 三级披露 + MCP + 技能归纳研究），后半段**没人管**：归纳出的东西无人审、无版本、无治理，失败的经验不留痕。因此器灵的定位是**技能的记忆与养护层**——**触发条件进目录卡、步骤骨架与坑按需注入、执行反馈派生成有效率、改进建议交人确认、冲突与危险由治理拦住**。人类练技能靠"练 + 反馈"，器灵管技能靠"**记 + 反馈 + 人审**"。

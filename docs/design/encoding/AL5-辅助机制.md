### T-AL5-01 · 配置模型与装载

- **里程碑**：M0
- **依赖**：无
- **产出**：`config/model.py`、`config/loader.py`
- **要求**：
  1. 数据类：`SpiritConfig` / `EmbeddingConfig` / `LLMConfig` / `BackendConfig`（字段见 LLD-AL5 §2.2，**该节已按实现重写**）

  - [ ] 环境变量能**覆盖** TOML 值；**且"覆盖默认值"也生效**（配置里没写该项时）
  - [ ] **无配置文件时用默认值启动**（缺失**不是错误**——这是"零门槛接入"的前提），

  - [ ] `api_key_env` 指向的环境变量缺失时，报错信息**不含 key 内容**

### T-AL5-03 · 生命周期装配骨架

## M1 · 运行时与可观测（T-AL5-04 ~ 08）

### T-AL5-04 · writer 线程与单写者串行化

- **里程碑**：M1
- **依赖**：T-AL5-03
- **产出**：`runtime/writer.py`
- **要求**：
  1. **所有写操作**经单一队列串行执行（写记忆 / 活性 / 审计 / 关联）
  2. `submit()` **必须非阻塞**（C1）
  3. 线程 `daemon=True` 且提供 `stop()`（C2）
  4. **主循环内单任务异常不得杀死线程**——try/except 包住，记录后继续（C4）
  5. 线程间通信**只用队列**，不用共享可变状态（C10）
  6. **"所有写操作"是字面意思**（P0-12 / P0-15）：**离线产出**（维护线程）与
     **宿主工具路径**（`spirit_remember` 等六个工具跑在宿主主线程）**都必须经队列**。
     两条都是**静默**违反的——`SQLiteBackend._write_connection()` 按**线程 id** 分配写连接，
     换线程写会先 `close()` 掉对方那条再新建，于是"单写者"当场作废、还每次多付一次建连接代价。
     `Services.write_now` 已改为**内置正确行为**（有 writer 就投队列 + 等落库），
     工具代码零改动——新增写路径时**照这个来**，不要另开直写
  7. **计数口径**：`flush()` 判据是 **堆 或 在途**；`pending()` = 堆 + 在途；
     `stop()` 的返回值与"是否 drain 干净"**一律用 `pending()`**——
     只看堆深会把"已出队、正在落库"那条算作已完成，**恰好在最需要报案的时刻把丢写报成 0**
- **约束**：R8 / INV-4 / D-03 / DES-REV-008 P0-12 / P0-15
- **验收**：
  - [ ] 队列满时 `submit()` 不阻塞（超时断言）
  - [ ] 所有写操作由**同一线程**执行（thread id 断言）
  - [ ] **`write_now` 在有 writer 时也由 writer 线程落库**（P0-15 的守门断言）
  - [ ] 并发大量 submit → 真实 SQLite 下**无 `SQLITE_BUSY`**
  - [ ] 单任务抛异常 → 线程存活且后续任务继续
  - [ ] **用例末行不得出现 `... or True` 之类的恒真兜底**；且覆盖路径要含**维护产出**这条跨线程写
    （P0-12：原用例只投 `kind="turn"`，恰好避开了唯一会跨线程写的路径）

### T-AL5-05 · 队列优先级与溢出策略

- **里程碑**：M1
- **依赖**：T-AL5-04
- **产出**：三个队列与优先级约定
- **要求**：
  1. `write_queue`：**不丢弃**（极端情况降级为丢弃 + 告警 + `status` 可见）
  2. `extract_queue`：丢弃最旧
  3. `maintenance_queue`：合并同类任务（`dedupe_key`）
  4. 优先级：**记忆写入 > 关联更新 > 提取 > 摘要**
  5. **两张档位表都必须穷举**（P1-43 / C8）：
     - `INTENT_PRIORITY`（**写意图 op**，与 AL2 的 `IntentOp` 一致）
     - `PRIORITY`（**任务类型 kind**）——DES-REV-003 只修了 op 那一半，
       `PRIORITY.get(kind, PRIORITY_MEMORY)` 让未登记的 kind **静默排进"记忆档"**，
       直到 DES-REV-008 P1-43 才补上 `kind_priority()`
     **未登记 → 抛 `ValueError` 并提示去登记**，不用"默认档兜底"
- **约束**：C8 / D-03 / DES-REV-008 P1-43
- **验收**：
  - [ ] 溢出时**摘要先于记忆被丢**
  - [ ] 队列深度可查询（供 `status`）
  - [ ] 合并策略生效（同 session 的重复 CommitTask 只保留一个）
  - [ ] **未登记的 `op` 与未登记的 `kind` 都抛错**（两条注入式用例，各守一张表）
  - [ ] **`INTENT_PRIORITY` 的键集 == AL2 `WriteIntent.op` 的取值集合**（跨层穷举断言）

### T-AL5-07 · `layers` / `reflect` / `audit_view`

- **里程碑**：M1
- **依赖**：T-AL5-06
- **产出**：`observability/status.py`、`observability/audit_view.py`
- **要求**：
  1. 全部为 **AL3 之上的只读投影**（模块级函数，不是 Protocol——LLD §2.3 已按实现重写）
  2. `reflect` 须能解释"为什么遗忘 / 为什么召回 / 哪些在成为候选信念"

- **验收**：
  - [ ] 三者均为纯函数（同输入同输出）
  - [ ] `audit_view(since, limit)` **过滤真实生效**（造多条审计事件，断言 `since` / `limit` / 倒序）

  - [ ] **`status` 与 `audit_view` 使用同一个投影实现**（`inspect` 断言：`status` 模块不重复拼装字典）

## M2 · 维护、收尾与合规（T-AL5-09 ~ 12）

### T-AL5-09 · maintenance 线程与调度

- **里程碑**：M2
- **依赖**：T-AL5-04
- **产出**：`runtime/maintenance.py`
- **要求**：
  1. 承担：巩固 / 衰减排序 / **L1 概览重算** / 摘要生成 / 记忆进化（M4）
  2. 调度间隔可配置（默认 30 min）
  3. **其写操作投递到同一 write_queue**，不持有独立写连接
  4. `submit()` 非阻塞；异常不杀线程（同 T-AL5-04 的 C4）
  5. **`thread_id` 必须缓存**（P1-44）：`Thread.ident` 在 `stop()` 之后变回 `None`，
     于是"维护任务跑在维护线程上"这条断言在收尾之后**问不出答案**——
     上一版用例正是因此被写成 `all(...) or len(set(seen)) == 1`（**半恒真的兜底**）
  6. **消费后必须销账**（P1-50）：`_loop` 里 `get()` 会把任务记成"在途"，
     消费完要 `notify_consumed()`，否则 `_inflight` 只增不减 → `stop(drain=True)` **每次白等满超时**
     （Windows 实测约 7.8s），而"已 drain 干净"这个承诺**是假的**
  7. **`action` 取值域要穷举**（P2-31）：`refresh_overviews` / `decay` / `optimize` / `consolidate`——
     未知 action **不得静默返回**（`if/elif` 落空 = 什么都不做）。这与"未知 kind 抛错"是**同一种病**
- **约束**：R8 / D-03 / DES-REV-008 P1-44 / P1-50 / P2-31
- **验收**：
  - [ ] 定时任务按间隔触发
  - [ ] **巩固确实在 maintenance 线程执行**（thread id 断言，且**收尾后仍可断言**——P1-44）
  - [ ] **`stale` 的 overviews 由 maintenance 重算，不在热路径**（呼应 T-AL2-07）
  - [ ] 单任务异常不影响后续调度
  - [ ] **`stop(drain=True)` 不空等**：无残留任务时**立即返回**（耗时上界断言——P1-50）
  - [ ] **未知 `action` 抛错或计数告警**（P2-31）

### T-AL5-10 · 关闭安全与崩溃恢复

- **里程碑**：M2
- **依赖**：T-AL5-09
- **产出**：`stop(drain=True)`、恢复路径
- **要求**：
  1. 关闭**必须 drain**：先 flush 再停线程，否则丢写
  2. `shutdown` **幂等**（可能被多次调用）
  3. 写队列**不持久化**——崩溃丢失属可接受（成员都是可重建的加工任务）；此决策须在文档中可见
  4. 崩溃后启动对账自动修复
  5. **无消费者时不空等**（P1-51）：`stop` 曾在"没有 writer/maintenance 线程"
     （CLI / `start_threads=False` 的测试）时**仍无条件 flush** → 白等满超时，而残留数又照报 0。
     要求：无消费者时不等待，**如实报 `pending()`**
  6. **`replay --rebuild-derived`（INV-12）的验收归属要写清**（P1-58 的**更正**）：
     这条**已在 AL3 落地**（`tests/test_store_m2.py::test_replay_restores_derived_fields`）。
     AL5 的 §8.4 是**引用**它——引用可以，但**必须在验收项里指名实装处**：
     否则下一个人（包括复核者）会以为"这一层的清单没人管"。
     > 原判"全仓无任何用例"是**错的**，取证方式正是它要防的毛病：**单向检索**。
     > *"全仓没有 X" 必须由全仓级检索支撑。*
- **约束**：INV-12 / DES-REV-008 P1-51 / P1-58（更正后）
- **验收**：
  - [ ] `stop(drain=True)` 后残留任务数为 0
  - [ ] `shutdown` 调用两次不报错
  - [ ] **无 writer 线程时 `stop()` 立即返回**（耗时上界断言——P1-51）
  - [ ] **`replay --rebuild-derived` 后派生字段与原始逐条相等**（实装处 = AL3 的 T-AL3-19；
        本层验收**引用**它并**指名出处**，不重复实现用例）
  - [ ] 写入过程中 kill 进程 → 重启后数据一致、无半写
  - [ ] 重启后对账通过
